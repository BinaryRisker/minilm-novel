# 从零训练一个会写小说的模型：零基础入门与本项目路线

更新：2026-09-17。面向没有机器学习基础、希望理解并推进 minilm-lab 的读者。项目状态按当天文件核对；这是一份介绍文档，不是已经完成训练的证明。

## 先回答最关心的问题

你要做的事情，可以理解为：给一个最初完全不会中文的程序安排教材，让它通过大量练习学会续写，再教它根据要求组织故事，最后让真实读者检查作品。

这件事可以从消费级显卡和小模型开始，但“程序能训练”“能写通顺段落”“能独立完成好看的小说”是三个不同阶段。30M 模型适合作为可控、能反复实验的起点，目前不能保证它最终能独立写出高质量长篇。

本项目选择的是：**随机初始化 → 中文语言学习 → 完整短故事 → 规划与场景写作 → 多场景短篇 → 人类检验。** 方向合理。当前已经有教学模型、数据处理、部分可靠性修复、远程训练辅助脚本、新分片模块，以及新增的 30M 模型定义和训练器；正式训练链路仍需在目标机器上验证。

补充阅读：[从零训练与基座微调：小说模型的完整比较](SCRATCH_VS_FINETUNING_NOVEL_GUIDE.md)，详细说明能力起点、数据格式、工具、显存、费用和交付差异。

建议第一次按顺序读第 1–5 节，建立概念；再读第 6–10 节，理解自己的机器和项目。参考资料放在最后，不需要先读完论文才能开始。

## 1. 我们到底在做什么

### 模型、训练程序、写作系统，是三样东西

| 名称 | 通俗解释 | 你最后能拿到什么 |
|---|---|---|
| 模型 | 内部有许多可调整数字的计算器，输入文字，预测后续文字 | 权重文件和结构配置 |
| 训练程序 | 组织练习、计算错误、调整那些数字的程序 | Python 代码、训练配置、日志 |
| 写作系统 | 调用模型写计划、写章节、保存人物状态、检查和导出作品 | 一套可运行的工具和完整小说文件 |

同一套写作系统接上不同模型，写作质量可能相差很大。一个网上的“AI 小说生成器”可能只是调用其他公司的模型，并没有训练自己的模型。

你的目标包含两件工作：训练自己的模型，以及让这个模型通过一套程序完成小说。先后都要做，且成绩要说明究竟来自模型自身，还是来自多轮规划、检索和修订。

### “从零”到底意味着什么

随机初始化就是：训练前，模型中的可学习数字是按指定规则随机生成的，没有继承现成模型学到的中文和世界知识。

可以使用 PyTorch、现成 Transformer 代码、自动求导、GPU 和分词工具。这些是造模型的工具，不是外部模型权重。像使用印刷机印自己的教材，并不等于抄别人的考试答案。

本项目还计划自己训练分词器。这里的“训练分词器”和“训练语言模型”不是同一个过程：前者学习怎样切文字，后者学习怎样根据上下文预测文字。

如果以后使用其他 AI 生成训练故事，模型权重仍可从随机初始化开始，但数据包含教师模型的影响，应如实标注为合成数据；这和加载预训练权重不是一回事。

## 2. 用一段小故事看懂训练

假设我们自己写了这样一段教材：

> 小雨在车站捡到一本蓝色笔记。她根据扉页上的地址找到失主，把笔记还了回去。

训练程序把它变成很多道“猜后续文字”的题，例如：

| 模型已经看到 | 希望模型提高概率的答案 |
|---|---|
| 小雨在车站捡到一本 | 蓝色 |
| 小雨在车站捡到一本蓝色 | 笔记 |
| 她根据扉页上的地址找到 | 失主 |

这只是便于理解的切法，真实切分由分词器决定，可能是单字，也可能是词的一部分。

模型第一次可能把“失主”排在很后面。训练程序比较预测和原文，算出一个误差值，叫 **loss（损失）**；PyTorch 计算哪些数字该往哪个方向改变，优化器按学习率做小幅调整。反复执行，模型逐渐把常见、合理的后续文字预测得更好。

“优化器”可以理解为调整方法；“学习率”是每次调整的幅度。太大容易学乱，太小可能学得很慢。

教材原文自动提供了答案，因此基础语言学习一般不需要人工为每个字打标签，这叫自监督学习。但程序只知道“下一个词是否接近原文”，并没有自动获得“这本小说是否精彩”的可靠判断。

### 训练和写作有什么区别

训练时，程序有原文答案，会修改模型权重。写作时，模型拿到题目或前文，选择一个后续 token，再把它接回输入，继续预测；通常不修改权重。这叫生成或推理。

例如模型刚生成“红色笔记”，下一次就要面对自己写出来的“红色”。错误可能继续传到后面。训练时总见到正确原文、写作时却要面对自己的历史，是长篇写作的一项实际困难。

### 模型是不是把小说存进去了

训练通常不是建立“书名→原文”的数据库，而是调整预测规律；但模型也可能记住并复述训练片段，尤其在重复很多时。因此，低 loss 不一定是学会写作，也可能是记住教材。要用没见过的作品和题目检验。

## 3. 小说数据从哪里来，怎样变成教材

### 数据来源

可以考虑五类来源：自己创作或明确授权的文本、公版作品、授权明确的开放数据集、通过许可取得的现代小说、注明来源的合成故事。

数据来源不同，教出来的能力也不同。主要读古典小说，输出容易带古典句式；主要读同一种网文，容易学到固定套路；大量翻译或合成故事可能带有生硬、重复的表达。原文质量比文件数更值得关注。

下载到本地只代表“有文件”，不自动说明它是完整作品、版本正确、无重复，或其来源允许所有后续用途。工程上要保存来源和用途记录；公开分享权重、原文与研究报告也应分别审查，不能仅凭仓库的一个许可标签作统一判断。

### 整理一篇作品，需要保留什么

下面是示意记录，不是当前程序的直接输入格式：

```json
{
  "story_id": "story_0001",
  "family_id": "original_work_0001",
  "source": "自行创作",
  "genre": "日常故事",
  "split": "train",
  "text": "小雨在车站捡到一本蓝色笔记……"
}
```

`story_id` 是这份文本的编号，`family_id` 把同一本书的章节、不同版本和改写归为一组。清洗要去广告、导航、无意义乱码，保留对白、段落、章标题等对写作有意义的信息。清洗规则要记录版本，避免今天和明天读到不同的“同一份数据”。

重复也分两种：逐字相同的副本，以及换了标点、章节、标题的近似副本。只比较文件名不够。训练集中的重复会浪费预算，跨训练/测试的重复还会让成绩虚高。

### 为什么不能把所有文件都拿来训练

我们希望知道的是模型能不能写没见过的故事，而不是能不能背熟已有故事。因此要留出一部分教材：

| 集合 | 可以怎样使用 | 不能怎样使用 |
|---|---|---|
| train，训练集 | 学习权重、拟合分词器 | 把它的成绩当泛化能力 |
| val/dev，验证集 | 选择配置、判断是否继续训练 | 反复调参后还称它是全新盲测 |
| test，测试集 | 在方案确定后最终检验 | 每次修改都查看，再据此选方案 |

例如 100 个作品家族，可以先按大约 80/10/10 分配；这是示例，不是固定标准。应先按作品家族划分，再切章节和训练片段。不能把同一本小说的前半本训练、后半本当独立新作品测试。

你的“所有本地小说一起纳入”可以实现为：所有来源进入统一清点和处理流程，符合数据质量要求的训练部分都有机会被使用。重复、损坏和保留测试数据不应为了凑“全量”硬塞进权重学习。

### “全部进入数据池”和“全部读过一遍”不同

如果训练池有 20 亿 token，本阶段预算只有 1 亿 token，就不可能把所有 token 都读过一遍。即使某个桶在数据池中，也不代表短阶段抽到了每一部作品。

想保证训练阶段覆盖每份合格训练文本，就需要按文档规划一轮遍历，并给足预算；想先验证能力，可以抽样小试。报告应该同时记录“可用数据量”和“实际读过多少、覆盖多少作品”。

混合采样还需要明确单位：按文件抽样、按 token 抽样、按题材比例抽样，会得到不同教材。一个桶文件多，不一定文本长。此前谈过的 60%–70% 等比例只是待测试假设，不能仅凭作品数占比认定为最佳配方。

## 4. Token、分片、参数，这些词是什么意思

**Token 是模型读写文字的小单位。** “小雨”“在”“车站”可能是三个 token，也可能拆得更细；一个 token 不等于一个汉字，更不等于一个字节。要先分词，才能知道数据究竟有多少 token。

**Tokenizer（分词器）是文字和编号之间的转换工具。** 比如“车站”对应编号 418。模型处理的是编号及其内部表示，输出后再转换为文字。本项目计划用训练集学习自己的词表。

**分片是提前把编号存成若干紧凑文件。** 它避免每次训练都重新处理几 GB 文本，也避免把所有 token 装进占内存很大的 Python 列表。memmap 可以理解为“需要哪一段，就从磁盘映射哪一段”。

例如编号用 uint16 存储，1 亿 token 约占 2 亿字节，即约 200MB，不计索引。它要求编号能装进 16 位；词表更大时需要其他格式。这个存储精度与模型训练时的 BF16/FP16 无关。

**30M 是约 3000 万个可学习参数。** 它不表示 3000 万篇小说、3000 万 token，也不意味着有 3000 万条可直接查询的知识。模型参数量相同，数据与训练方式不同，效果仍会很不一样。

**Context（上下文长度）是每次计算能看到多少 token。** 1024 token 的模型可以分多次输出比 1024 更长的文字，但每次不会自动看见全部历史。超出部分要靠选取前文、摘要和状态记录重新提供。能不停写不等于能记住整本书。

**Batch 是一次练习的数量，step 是一次参数更新。** 单卡 micro-batch=1、每段 1024 token、累计 8 次梯度，理想情况下每次更新处理约 8192 个有效 token。若有 padding 或被遮掉的目标，要按真正计算 loss 的 token 计数。

**Epoch 是一轮数据遍历。** 随机窗口采样计算出来的“等效 epoch”只是曝光量换算，未必保证每个位置都访问过。

**Checkpoint 是训练存档。** 除权重外，完整存档还要保存优化器、随机状态、学习率进度和读到的数据位置。只有模型权重，通常不能原样继续之前的训练过程。

## 5. 有哪些实现路径

| 路径 | 大致做法 | 优点 | 与本项目的关系 |
|---|---|---|---|
| 调用现成模型 | 接口输入题目，程序管理章节和记忆 | 最快验证写作产品流程 | 不能证明自己的模型从零学会写作 |
| 微调现成模型 | 继承已有语言能力，再学目标风格/任务 | 通常比从零更快得到实用效果 | 不符合你要求的随机初始化路线 |
| 从零训练小模型 | 自己准备数据、初始化、预训练，再训练写作任务 | 谱系清楚，便于研究和分享实验 | 当前主路线 |
| 从零训练更大模型 | 类似流程，但扩大模型、数据与算力 | 更大的能力空间 | 成本和工程难度更高，不宜跳过小规模验证 |

另外还有“检索增强”和“规划代理”等系统方法，它们可以搭配上述任一模型。检索是把相关旧内容找出来给模型看；规划是先列故事结构再写。两者不会自动让一个还不会写通顺句子的模型具备小说能力。

本项目应坚持从零训练，同时借用成熟代码和工作流。先把短故事写完整，能帮助区分“训练程序有问题”“数据不合适”“容量或训练预算不够”，而不是一开始就把所有问题混在长篇里。

## 6. 需要哪些工具和框架

| 工具 | 负责什么 | 本项目怎么用 |
|---|---|---|
| Python | 组织数据、训练和生成程序 | 主开发语言 |
| PyTorch | 模型计算、自动求导、GPU 加速 | 正式训练核心框架 |
| Tokenizers 或 SentencePiece | 学习分词规则、把文字转换成编号 | 可选成熟实现；仍只在自己的训练集拟合 |
| NumPy / memmap | 紧凑数组、磁盘分片访问 | 让大量小说不必一次装进内存 |
| Git 与配置文件 | 记录代码和实验设置 | 每次实验能知道用了哪版程序 |
| JSONL 日志 / TensorBoard | 记录、观察 loss 与速度 | 先记录完整，再考虑可视化平台 |
| SSH、文件传输工具、tmux | 使用远程 GPU、传文件、保持任务运行 | AutoDL 的日常操作层 |

Transformer 是模型架构，PyTorch 是实现它的工具，AutoDL 是出租机器的平台。三者不是互相替代的东西。Hugging Face Transformers 又是一个可选模型库：既能加载预训练权重，也能按配置随机建模型；是否从零训练取决于初始化方式，不取决于用了哪个库。

你无需从头手写求导或 GPU 内核。现有手写 JS 模型适合理解数学，正式训练可以继续使用成熟框架。PyTorch 官方入门覆盖数据、模型、求导、优化和保存，正好对应这条学习链。[官方入门](https://docs.pytorch.org/tutorials/beginner/basics/intro.html)

分词工具也支持从头训练自己的词表。注意官方示例可能是为了演示 API，把不同数据文件一起读入；本项目做严格评估时只让 tokenizer 读取 train。[Tokenizers 官方教程](https://huggingface.co/docs/tokenizers/quicktour)

## 7. 你的 AutoDL 机器是否合适

截图是单卡 RTX 3080 Ti、12 核 CPU、90GB 内存、30GB 系统盘、50GB 数据盘。NVIDIA 官方给桌面 RTX 3080 Ti 的标准显存为 12GB，具体租用实例仍以 `nvidia-smi` 为准。[官方规格](https://www.nvidia.com/en-us/geforce/graphics-cards/30-series/rtx-3080-3080ti/)

这是一台适合尝试 30M 稠密模型的机器。是否能容纳某个上下文和 batch、每小时能训练多少 token，需要运行实际配置测量；不能仅凭 GPU 型号承诺训练时长。

| 资源 | 可以理解为 | 与训练的关系 |
|---|---|---|
| 显存 | GPU 的工作台 | 放模型、梯度、优化器状态和本批计算中间结果 |
| 系统内存 | CPU 的工作台 | 数据处理、缓存、文件加载；90GB 不能当作 90GB 显存 |
| 数据盘 | 仓库 | 存语料、token 分片、checkpoint、日志 |
| GPU 算力 | 做练习的速度 | 决定同一任务的运行时间，但也受数据读取影响 |

约 30M 参数若只用 FP32 保存权重，文件主体约 120MB；训练时还要保存梯度和 Adam 等状态。以参数、梯度及两份 FP32 动量估算，约 480MB，**尚未计入激活、临时张量和框架开销**。完整存档大小取决于保存内容，不能统一写成 360MB。

先试 context 512/1024、micro-batch=1，再增加到实测稳定的档位。梯度累计让多小批合起来再更新参数；混合精度降低部分计算与存储成本；激活检查点用重新计算换显存。它们改善资源使用，不替代数据质量。

不建议现在承诺“batch=32 肯定能跑”或“3080 Ti 固定是 4090 的几成速度”。项目旧说明中有这样的估计，应当把它们视为待实测数字。

### 时间和费用怎样算

先用目标模型、真实数据路径预热并测量稳定的有效 token/s。然后：

```text
训练小时 ≈ 计划训练 token ÷ 有效 token/s ÷ 3600
租用费用 ≈ 实际计费小时 × 控制台单价
```

例如假设测得 5000 token/s，训练 1 亿 token 约 5.6 小时，3 亿约 16.7 小时。这只是算术示例，不是对该显卡的实测预测；验证、存盘、预处理和闲置还会增加时间。

先本地准备好代码和数据清单，再租卡跑短测。长期运行要有日志、存档和中断恢复；浏览器页面关闭不应中断任务。下载并校验结果后再根据 AutoDL 控制台显示确认实例状态和计费状态。

### 磁盘要存哪些东西

优先上传训练需要的处理后正文或分片、对应清单、代码和配置。原始下载压缩包可以保留在本地用于溯源，不必为训练把所有历史缓存再上传一遍。避免同时长期保留压缩包、解包数据、多代 token 分片和无限 checkpoint。

50GB 可能够首轮使用，但应按最终包和分片实测，预留解压临时空间及多个恢复点。系统盘和数据盘分别检查，路径以实例挂载信息为准。M4 16GB 可承担数据检查、轻量实验和推理验证，不能和服务器显存相加使用。

## 8. 一次从零到一的训练，会经过哪些阶段

```text
小说文件 → 清洗与家族去重 → 固定 train/dev/test
    → train 拟合分词器 → 编码为分片
    → 随机初始化模型 → 预训练 → 完整故事课程
    → 自模型规划与场景训练 → 导出 → 完整小说和真人评审
```

### 阶段一：先证明程序能训练

使用几十条干净短文本和微型模型，让它能明显记住一个小样本，这是排查训练程序的实验，不是质量成绩。检查 loss 是否下降、保存加载是否一致、恢复是否接着原位置训练、模型是否只看过去。

完成后再测 30M 候选的显存和吞吐。这个阶段的输出是“训练机器确实能工作”的证据。

### 阶段二：让模型学中文续写

用混合的训练正文进行基础预训练。普通正文自带下一个 token 的答案，不必先给每章人工写大纲。先短预算看曲线和完整样本，再延长训练。

这一步主要得到续写能力。用户输入“请写一个温暖的故事”，模型不一定会遵从，因为自然小说正文未必教过它“题目→回答”的格式。

### 阶段三：教它按要求完成短故事

加入“题目/人物/约束→完整故事”的成对样本，例如：

```text
输入：写小雨归还笔记的故事。她起初犹豫，最后作出决定。
目标：一篇包含犹豫、行动、结果的完整正文。
```

从自己的预训练存档继续学习，这也属于监督微调，但没有使用外部预训练模型。可以人工写样本，也可对可靠正文制作题目与摘要；测试时不能把参考故事答案反抽出的完整情节塞给模型，再称它自主构思。

此阶段先要求 300–800 字。模型知道怎样结束、人物做事有原因，比字数越长越好更有价值。

### 阶段四：教它规划与跨场景保持状态

将任务分成：题目→计划、计划和已有状态→场景、场景正文→新的状态。仍可由同一个自训练模型分别完成。

对于小雨的故事，状态可以记录“笔记是蓝色”“小雨在车站”“失主尚未找到”。每次更新都要能在正文找到依据。“下一章将找到失主”是计划，不能立刻记成已经找到。

先写三个相连场景，再挑战完整短篇。若给正确计划仍写不好，先改善正文能力；若给正确计划能写好、自主计划不行，再集中训练规划。

### 阶段五：导出并交给读者

把模型权重、分词器、配置、推理代码一起交付。在新环境、不调用外部写作模型的情况下生成完整作品。

固定题目、种子和修订预算，保留所有结果，不只展示最好的一篇。匿名请读者完整阅读，检查语言、因果、人物一致性、结局和吸引力。自动检查能发现重复或长度问题，不能替代文学判断。

训练 loss 下降、程序成功退出、文章写得漂亮，都不能单独证明已经获得小说能力。

## 9. 当前项目实现是否合理，路径是否正确

结论：基础路线正确，已经积累了有用的教学和工程工作；当前最需要的是把正式训练链路真正接通，并用完整短故事结果验证。

按 2026-09-17 的文件状态：

| 部分 | 当前看到的实现 | 应怎样理解 |
|---|---|---|
| 手写模型与 PyTorch 对齐 | `py/minilm_torch.py`、对齐脚本 | 已有数学实验基础，不等于小说模型 |
| 数据清单与处理 | `py/data/`、`py/splits.py` | 已有来源、分桶、切分和校验设施；全量版本仍需统一 |
| 教学分词器 | `py/tokenizer.py` | 已有学习版 BPE；尚非新训练线完成集成的正式分词器 |
| 新数据分片 | `py/novellm/dataset.py` | 今天新增了流式字符词表、uint16/memmap 与边界偏移记录，是实际进展 |
| 设备和上云辅助 | `doctor.py`、`dev/autodl/` | 可以辅助准备远程运行；不能代替目标模型的 GPU 实测 |
| 30M 模型与正式训练器 | 已新增 `py/novellm/model.py` 和 `trainer.py` | 2026-09-17 补充核对：已存在模型、分片训练和存档相关代码；不代表正式 GPU 训练与小说质量已经验收 |
| 自主规划、状态、短篇人评 | 主要是设计和协议 | 尚无足够证据宣称完整实现和验收 |

新分片模块主要沿用旧模型的字符编码语义；记录了文档边界不代表所有采样已经按边界隔离。新增训练器已接入分片读取，正式开训仍应核验结束符、采样策略、实际数据校验与恢复身份。这一节是代码范围核对，不是本轮完整验收。

### 前面讨论中，需要澄清的几个地方

**先前“全部优化”的完成范围说得过宽。** 当时完成了部分恢复、数据检查、doctor 和缓存修复，但完整缓存身份、测试隔离、30M 训练、故事 pipeline 并没有全部落地。应以具体模块和验收证据为准。

**旧手册中的训练命令是未来接口。** `python -m py.novellm.train` 等命令所需模块目前不存在，不能直接复制运行。入门阶段只需理解运行顺序；正式操作文档应在实现后用实际命令重写并试跑。

**“从零训练”的硬要求是模型参数不能继承外部预训练权重。** 自建 tokenizer 是本项目额外选择，不必把“使用别人 tokenizer”与“继承别人模型全部知识”混为一谈。

**之前的数据体量存在不同版本和统计口径。** 对话中的 19.28 万条、2.43 亿字符来自某份清单；处理目录曾统计到约 22.68 万文件、5.67GB；新文档又出现十几亿到二十几亿字符的描述。这些数不应混用。可能存在新旧清单、截断正文与全文、旧文件残留等差异，需要核对，不能凭介绍文档确认哪份就是全量。

正式开训前应出一张数据盘点表：所选清单版本、清单外文件数、实际可读正文字符、分词后 token、去重后作品家族数、训练/验证/测试量和缺失/不匹配记录。每个未纳入文件都有原因，才算满足“所有本地数据都被处理过”。

### 下一阶段最值得做的事

先把清单和实际文件统一，冻结正式 tokenizer，核验新增 30M 模型、分片数据和可恢复训练器；跑微型全流程，再在 3080 Ti 上做真实短测。之后按预算逐步预训练，尽早让人阅读完整短故事。

不必继续把“超过 trigram 的下一字 Top-1”作为主要目标。它有教学和诊断价值，但无法判断人物是否可信、故事是否有结局。也不宜在基础语言能力不足时先堆很多规划代理、奖励模型或强化学习步骤。

## 10. 可以参考哪些资料和案例

按入门顺序选读即可。借用代码或方法不等于采用其权重；以下大模型项目也不是本项目已复现的成绩。

| 资料 | 建议看什么 | 不要据此推断什么 |
|---|---|---|
| [PyTorch：Learn the Basics](https://docs.pytorch.org/tutorials/beginner/basics/intro.html) | 数据→模型→loss→更新→保存的基本循环 | 不必一次学完分布式训练 |
| [Tokenizers：从头训练分词器](https://huggingface.co/docs/tokenizers/quicktour) | 文字、词表、编号、保存加载；本项目只用 train | 分词器本身不会写小说 |
| [nanoGPT](https://github.com/karpathy/nanoGPT) | 小型 GPT 的模型和训练代码，理解完整循环 | 小样例跑通不是中文小说质量保证 |
| [TinyStories 论文](https://arxiv.org/abs/2305.07759) | 受限故事如何降低小模型学习难度 | 英语短故事结果不能直接外推中文长篇 |
| [SimpleStories 训练仓库](https://github.com/simple-stories/simple_stories_train) | 面向小语言模型的可参考训练实现 | 仍需要自己的中文数据和评测 |
| [LongWriter](https://github.com/THUDM/LongWriter) | 长输出训练数据、规划和长文评测 | 它依赖预训练基座，不是消费显卡从随机初始化的直接模板 |
| [AI_NovelGenerator](https://github.com/YILING0013/AI_NovelGenerator) | 设定、章节、记忆、校对怎样组成产品 | 这是调用模型的写作系统，不证明自己训练了小说模型 |
| [ConStory-Bench](https://arxiv.org/abs/2603.05890) | 长篇事实、时间、人物等一致性错误怎样定位 | 自动检查器不能完全替代人评 |
| [有限数据混合预训练研究](https://arxiv.org/abs/2605.12715) | 数据比例与重复曝光应联合考虑 | 论文中的最佳重复次数不是本项目固定配方 |

研究阅读可以放在基本循环跑通后。对你最有帮助的顺序是：先看 PyTorch 的训练循环，再看 nanoGPT 的小模型，再看 TinyStories/SimpleStories 为什么设计那样的数据，最后才读长篇规划和评测论文。

## 11. 怎样把过程写成可分享的文章

每完成一个真实阶段，就写一篇围绕一个问题的文章：

1. “我到底有多少可用小说”：数据来源、清洗、重复、版本与最终盘点。
2. “模型怎样学会下一个字”：微型实验，展示 loss 和原始输出。
3. “30M 在 3080 Ti 上需要多少资源”：实际配置、显存、token/s、恢复和成本。
4. “读过小说为什么还不会按题目写”：续写与条件故事训练的差异。
5. “加大纲和记忆真的有效吗”：同题目、同预算、全部样本比较。
6. “读者愿意读完吗”：匿名完整阅读、分歧、失败样本及后续修订。

每篇都应保留具体数据版本、代码版本、配置和结果路径。可以先写失败：比如“loss 降了，但故事没有结尾”，这种证据比提前宣称“模型已经达到人类水平”更有研究价值。

第一次正式里程碑可以定义得很具体：**在新环境中加载自己从随机初始化训练的权重，用固定题目生成一篇完整短故事，并让未参与训练的人读完评价。** 这一步跑实，再逐渐延长故事，项目才真正开始从教学实验走向可验收的小说模型。
