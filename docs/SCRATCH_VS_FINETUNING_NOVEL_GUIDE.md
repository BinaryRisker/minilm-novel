# 从零训练与基座微调：小说模型的完整入门比较

日期：2026-09-17。面向第一次接触模型训练的读者。

本文比较两条路线，不改变本项目“正式模型必须随机初始化”的要求。硬件以拟租用的单卡 RTX 3080 Ti、90GB 内存为背景；未进行该服务器的性能实测，费用示例均不是报价。

## 1. 先用一个比喻建立概念

**从零训练**：给一个还不认识字的学生安排全部课程。他需要从文字规律开始，逐步学习句子、人物、事件和故事结构。

**微调已有基座**：请一位已经读过很多书的人参加写作训练班。你主要教他写什么题材、遵循什么要求、用什么输出格式。

这个比喻也有边界：模型没有人类的生活经验。它通过训练调整大量数字，让预测和生成更符合样本中的规律；两条路线都可能写出矛盾和重复内容。

“30M”表示约三千万个参数，即三千万个可调整的数字。“3B”表示约三十亿个，约为前者的 100 倍。参数不是书籍数量，也不是知识条目。

最重要的区别是**起点**：从零模型的参数最初是随机数；微调模型的参数已经承载了前人训练得到的能力。下载模型只支付下载和后续使用成本，不代表此前训练成本不存在。

## 2. 四件经常混淆的事

| 维度 | 回答的问题 | 例子 |
|---|---|---|
| 初始化 | 起初有没有继承模型权重？ | 随机初始化、加载预训练权重 |
| 模型规模 | 总共有多少参数？ | 30M、1B、3B、7B |
| 训练阶段 | 这次主要教什么？ | 语言预训练、领域继续预训练、指令微调、偏好优化 |
| 更新方式 | 哪些参数参与更新？ | 全参数更新、LoRA、QLoRA |

因此，以下说法可以同时成立：

- 一个模型从随机初始化开始，先预训练，再用自己训出的权重做指令微调。它的血统仍然是从零训练。
- 一个 3B 基座只训练 10M 个 LoRA 参数。运行时仍然需要约 3B 的基座，不能称为“独立的 10M 模型”。
- 全参数微调会更新整个基座，但它仍然继承预训练能力，不属于从零训练。
- 使用现成模型代码和开源框架，不等于使用现成模型权重。可以用库里的模型结构，以随机参数开始训练。
- 使用别人训练好的 tokenizer，不等于加载别人模型的语言知识。Tokenizer 主要定义文字如何编码；是否自建是另一项实验选择。

## 3. 两条路线究竟分别做什么

### 3.1 从零训练小模型

典型流程：

```text
准备原始文本 → 清洗去重与划分 → 建立 tokenizer
→ 定义模型并随机初始化 → 预训练 → 检查续写能力
→ 用任务样本训练按要求写故事 → 人类评测 → 迭代
```

例如给模型看到“雨停了，小雨走出”，要求它预测下一个 token。预测错误就微调参数，重复很多次。原文自动提供了答案，不需要人给每个字手工打标签。

它一开始连中文句式都不会。你提供的数据既承担“识字和语言学习”，也承担“小说写作学习”。只喂某种小说，可能学到题材习惯，却缺乏常识、其他文体和指令理解能力。

优点是模型结构、数据来源、实验过程都更可控；小模型便于反复运行。困难是基础能力必须自己建立，30M 容量也限制了它能同时学好的东西。程序跑通是工程成果，不自动等于小说质量合格。

### 3.2 使用已有模型微调

典型流程：

```text
选择并测评基座 → 固定权重版本和 tokenizer
→ 准备领域文本或任务样本 → 选择全量 / LoRA / QLoRA
→ 训练 → 与原基座盲评 → 保存与部署
```

微调前应先让原基座完成你的题目，建立对照。否则无法判断结果是你训练带来的改善，还是它本来就会。

基座名称中的 **Base** 通常指预训练模型，倾向于续写输入；**Instruct/Chat** 通常已经接受过指令或对话训练，更容易按要求回答。具体能力还应实测。对话模型需要遵循它规定的消息模板，随意拼接格式可能损害效果。

微调也不一定只是“给几个问答”：它可能是继续学习大批原文，也可能是学习任务输入与正确输出。两者的数据格式和目标不同。

## 4. 小说数据怎么用：同一本书能变成不同课程

假设你有一篇原创故事：小雨在车站捡到蓝色笔记本，通过里面的线索找到失主。

### A. 语言预训练或领域继续预训练

输入主要是清洗后的正文：

```text
雨停以后，小雨在车站长椅上看见一本蓝色笔记本……
```

模型学习接下来的文字。随机初始化模型用它建立语言能力；已有基座用它适应题材和语言风格，通常称为领域继续预训练。

**小说原文天然适合续写学习，但没有明确教会“看到这个任务就完成这个任务”。** 读了很多正文，不代表模型自然学会列大纲、检查设定和按字数收尾。

### B. 指令微调，通常称为 SFT

把写作任务与示范答案配对，例如：

```json
{
  "prompt": "写一篇有明确结局的短故事。主角小雨在车站捡到蓝色笔记本，通过线索归还失主。",
  "completion": "雨停以后，小雨……最终，她把笔记本交回了失主手中。"
}
```

还可以分别构造：故事要求→大纲、大纲与当前状态→场景、正文→状态更新、存在矛盾的段落→修订稿。关键是答案确实符合输入，且没有把未来情节误写成已经发生的事实。

SFT 经常只对答案部分计算损失，但训练仍需处理输入部分。不同框架默认行为不同，应检查掩码和模板；具体能力见 [TRL SFT Trainer 文档](https://huggingface.co/docs/trl/main/en/sft_trainer)。

### C. 偏好优化，例如 DPO

同一写作要求给出两个候选，人类判断哪个更好，并记录理由或选择。它适合已有一定写作能力之后细化偏好，不适合拿来代替基础语言学习。成对样本若只是“长答案总是更好”，模型可能学到的是堆字数。

### “所有本地小说一起纳入”应怎么理解

应让所有文件进入**盘点与处理流程**，但不把每个文件不加判断地全部用于训练：

1. 记录来源、编码、长度和内容哈希；把广告、乱码、重复备份等单独标记。
2. 识别作品和近重复版本，同一作品的章节与改版尽量进入同一数据集合。
3. 先划分训练、验证和测试，再制作训练片段。测试材料不能也喂给模型。
4. 保留文档边界和结束符，明确长篇怎样切块、短篇怎样拼接；不要误教模型将两本书连成同一故事。
5. 统计清洗后独立 token 数、每轮实际处理 token 数和各题材占比。多个 epoch 只是重复学习，不是获得了新的独立数据。

从零训练更依赖足够且多样的基础文本；微调更依赖样本与目标任务是否匹配。不要把全部原文机械转换成重复的“请续写”。可以先人工检查一小批任务样本，确认格式和质量，再扩大。样本量是否足够，靠未见题目上的表现判断，没有通用的合格数量。

## 5. 能力、风险和控制范围比较

| 比较项 | 随机初始化小模型 | 已有基座微调 |
|---|---|---|
| 起始中文能力 | 需要从数据学起 | 取决于基座，通常已有基础 |
| 常识与知识 | 主要来自自己的训练材料 | 继承基座知识，也继承它的错误 |
| 指令遵循 | 需要专门建立与验证 | Instruct 基座一般更有起点优势 |
| 参数与结构控制 | 很高，可改变层数、词表和结构 | 通常沿用基座，改动可能破坏权重兼容 |
| 数据需求 | 同时承担基础学习与任务学习 | 可集中补足题材、风格和任务行为 |
| 基础训练透明度 | 能记录自己使用的全部语料 | 通常无法完全知道原训练语料 |
| 训练调试 | 数据、结构、优化器都可能出问题 | 起点较成熟，但模板与数据错误仍常见 |
| 过拟合 | 小数据反复学习可能记忆原文 | 少量样本过强训练也会背诵、模式僵化 |
| 遗忘 | 后续阶段也会损害先前能力 | 微调可能损害已有常识或其他任务能力 |
| 写作提升空间 | 受容量、数据和训练共同限制 | 受基座能力、样本和训练共同限制 |
| 长篇一致性 | 很难，需要单独训练和评测 | 也不会因一次微调而自动解决 |
| 推理开销 | 30M 通常较轻 | 跟基座规模有关，LoRA 不让 7B 变成小模型 |
| 成果归因 | 更适合研究“能力怎样学会” | 需要与未微调基座对照 |
| 外部依赖 | 仍依赖框架、数据与运行环境 | 还依赖基座、tokenizer、版本及许可 |
| 快速获得可用写作效果 | 风险较高、迭代可能较长 | 通常更有利，但必须实测 |

微调不是给模型安装一个内容精确的数据库。人物档案、时间线等经常变动的信息，更适合保存在外部文件或数据库，生成时检索并提供给模型。这个做法属于检索和上下文管理，不等于模型训练。

## 6. 全参数微调、LoRA、QLoRA 有什么区别

**全参数微调**：原模型的大多数或全部参数都更新。适应范围大，梯度和优化器状态也多；更需要控制学习率和遗忘。

**LoRA**：冻结原权重，在部分层添加可训练的小矩阵。比喻为保留原书，在旁边放一套可调的批注。训练和保存的新增参数较少，但计算仍会经过大基座。不能根据“只训练 1% 参数”推断“耗时只有 1%”。参见 [PEFT LoRA 官方说明](https://huggingface.co/docs/peft/main/en/conceptual_guides/lora)。

**QLoRA**：让冻结的基座以低比特形式存储，再训练 LoRA。原论文使用 4-bit 量化，并不是所有运算和所有状态都变成 4-bit；计算及适配器仍涉及更高精度。它降低显存需求，但具体速度、质量和兼容性取决于实现。参见 [QLoRA 论文](https://arxiv.org/abs/2305.14314)。

三者都没有免除数据清洗和评测。LoRA/QLoRA 是节省资源的训练方法，不是“保证模型不会遗忘”或“少量小说即可训练作家”的保证。

## 7. 要用什么工具

| 工具层 | 从零路线 | 微调路线 | 通俗解释 |
|---|---|---|---|
| 系统与环境 | Linux、Python、PyTorch、GPU 驱动 | 同左 | 训练程序的运行环境 |
| CUDA 与 GPU 后端 | NVIDIA 卡常用 | NVIDIA 卡常用 | 让计算在显卡上进行 |
| 文本处理 | 自己的清洗脚本、NumPy、可选 Datasets | 同样需要 | 把资料整理为稳定样本 |
| Tokenizer | 自建或选择后冻结 | 通常沿用基座 tokenizer | 把文字编码为数字 |
| 模型实现 | 当前 MiniLM/novellm 或库中随机初始化模型 | Transformers 等加载基座 | 定义模型怎样计算 |
| 训练器 | 自己的训练循环或成熟 Trainer | Trainer、TRL 或整合框架 | 喂数据、更新参数、存档 |
| 参数高效训练 | 初期不是必需 | PEFT、可选 bitsandbytes 等 | 支持 LoRA 与低比特训练 |
| 操作入口 | 当前项目命令与配置 | 可选 LlamaFactory | 将复杂设置组织成可操作流程 |
| 记录与恢复 | 日志、配置、数据版本、checkpoint | 同左，另记录基座版本 | 知道怎么重现实验和续跑 |
| 效果评测 | 自动指标和人工盲评 | 同左，另比较原基座 | 判断模型是否真的变好 |

PyTorch 是计算框架，不是现成的小说作者。Transformers 是模型与训练相关工具库，使用它既可以加载预训练权重，也可以随机初始化。LlamaFactory 是整合工具，不会替你判断数据是否足够或小说是否好看。

参考 [LlamaFactory 项目](https://github.com/hiyouga/LlamaFactory) 和 [nanoGPT](https://github.com/karpathy/nanoGPT)。初学者不需要同时掌握所有工具；本项目应先固定一套可复现环境。不要因为镜像版本号更新就认为更适合，尤其要核对 PyTorch、CUDA、量化库和驱动的兼容性。

## 8. 显存为什么不能只看权重文件大小

训练时显存里可能同时有：权重、梯度、优化器状态、中间计算结果、临时缓冲。上下文越长、单批样本越多，通常越耗显存。高效注意力可避免保存完整注意力矩阵，所以不能用单一平方公式估算所有实现。

下面仅展示**参数存储量**，使用十进制 GB，省略元数据；实际文件和显存会有额外开销。

| 总参数 | FP32 权重 | FP16/BF16 权重 | 理想 4-bit 权重主体 |
|---|---:|---:|---:|
| 30M | 0.12GB | 0.06GB | 0.015GB |
| 1B | 4GB | 2GB | 0.5GB |
| 3B | 12GB | 6GB | 1.5GB |
| 7B | 28GB | 14GB | 3.5GB |

4-bit 一列不是 QLoRA 的训练显存：量化比例、量化元数据、未量化层、适配器与激活都要另算。

再用一个明确假设帮助理解：如果权重、梯度、Adam 两份状态均为 FP32，合计约为每参数 16 字节；30M 约 0.48GB，3B 约 48GB，**都还没有激活和临时空间**。混合精度是否保存 FP32 主副本会改变估算；并非训练都遵循 16 字节。参见 [Transformers 显存构成说明](https://huggingface.co/docs/transformers/main/en/model_memory_anatomy)。

### 你的 3080 Ti 是否合适

桌面版 RTX 3080 Ti 官方规格为 12GB 显存，租机时仍需用 `nvidia-smi` 核对实际分配。规格参考 [NVIDIA 官方页面](https://www.nvidia.com/en-us/geforce/graphics-cards/30-series/rtx-3080-3080ti/)。

- **约 30M 从零训练**：是合理的单卡实验起点。先以短上下文和小批量实测，再定正式配置。
- **1B–3B 量级 QLoRA**：可作为另一条路线的候选，需要核对具体结构、序列长度和软件支持。
- **7B QLoRA**：部分配置可能可行，但 12GB 下余量有限，不能承诺任意上下文和批量都能跑。
- **7B 的 FP16 基座加普通 LoRA**：仅权重主体就约 14GB，无法全部常驻 12GB 显存；卸载到 CPU 会引入速度和实现上的代价。
- **大基座全参数微调**：显存压力远大于适配器微调，不能用“量化权重能放进去”证明全量训练可行。

90GB 主内存有利于预处理，但不能等同为 90GB 显存。50GB 数据盘需要同时容纳数据、分片、模型下载缓存和多个 checkpoint，尤其微调基座时要预留空间。Mac mini M4 的统一内存和软件后端不同，不能把 NVIDIA 上的 QLoRA 命令无修改照搬。

## 9. 成本如何算：不要只比较租机单价

训练总成本可以拆成：数据整理与标注、GPU 运行、失败与重跑、存储与传输、评测人工、后续部署。个人项目最容易忽略的是整理数据和反复读完整故事的时间。

计算租机费的基本方法：

```text
训练处理 token 数 = 每轮处理 token 数 × epoch 数
纯训练小时 ≈ 处理 token 数 ÷ 实测 tokens/秒 ÷ 3600
租机费用 ≈ 全部计费小时 × 每小时价格 + 其他计费项
```

最后一项应包含付费实例上的预处理、验证、保存、等待等时间。正式计费规则以平台订单为准。吞吐要在预热后、相同上下文和批量条件下测量，单步初始化时间不能代表稳定速度。

**下面只是算术示例，不是 3080 Ti 的性能预测，也不是 AutoDL 报价：**

| 假设实验 | 假设处理量 | 假设实测速度 | 纯训练时间 | 若假设每小时 2 元 |
|---|---:|---:|---:|---:|
| 30M 从零预训练 | 3 亿 token | 5,000 token/s | 约 16.7 小时 | 约 33.3 元 |
| 3B QLoRA，1 万样本，每样本平均 1,000 token，1 轮 | 1,000 万 token | 500 token/s | 约 5.6 小时 | 约 11.1 元 |
| 上一项训练 3 轮 | 3,000 万 token | 500 token/s | 约 16.7 小时 | 约 33.3 元 |

该表只演示如何估算，**不代表这些训练量足够，也不代表三个结果质量相当**。SFT 的输入和答案都参与计算；用于计算损失的答案 token 数与实际处理 token 数不是一回事。填充、打包和样本长度分布也影响吞吐。

两个重要结论：

1. **小模型单步便宜，不等于达到写作目标的总成本低。** 如果必须自己学全部基础能力，可能需要更多数据和多轮路线迭代。
2. **微调参数少，不等于整个模型计算少。** 一个大基座的前向计算和中间状态仍然有成本；反复高质量标注与人评也可能成为主要投入。

30M 从零与 3B 微调还混合了“规模”和“是否预训练”两个变量。公平研究初始化影响，应尽量比较相近规模、明确训练数据与预算；选择实用路线则应比较达到同一人评目标的总成本。

在没有你服务器的实际吞吐、清洗后 token 数和实时单价前，任何“总共几十元”“一定两天训完”都不可靠。

## 10. 保存、续训和部署也不一样

从零模型交付通常需要：模型权重、结构配置、tokenizer、生成代码、运行依赖和说明。若要精确续训，还需要优化器、学习率调度、随机状态、数据读取位置等训练状态；只有权重一般不够。

LoRA 交付可以只保存适配器与配置，但使用者仍需获得匹配的基座和 tokenizer，并知道准确版本。适配器能否合并、如何合并与量化实现有关；合并后总模型仍是原来的规模。参见 [PEFT checkpoint 格式](https://huggingface.co/docs/peft/main/en/developer_guides/checkpoint)。

两条路线都能本地离线运行，微调不意味着必须使用在线 API。但部署大基座通常比部署 30M 更费内存和算力。量化可降低推理存储，并可能影响性能与质量，需要测试。

模型许可、基座许可、训练材料来源是不同问题。随机初始化不自动消除训练数据的使用限制；LoRA 也不是绕过基座许可的办法。应保留来源记录并按实际许可决定分发方式，不能简单宣称“用了某类材料，所以所有结果必然可以或必然不可以分享”。

## 11. 两条路线都会遇到的小说难题

句子通顺只是第一关。真正的小说还涉及人物动机、时间顺序、伏笔回收、情节推进、文风稳定以及完整结局。长上下文表示一次能接收更多输入，不表示模型一定能正确使用所有信息。

常见问题包括：人物突然改名、已损坏的物品恢复、角色知道不该知道的事、每段都在总结、反复出现类似对白、无限延长而不结束。

可用的改进手段包括大纲、场景分解、人物与世界状态、检索记忆、生成后检查和修订。但这些手段依赖模型能正确执行相应任务；给小模型套一个复杂流程，不保证它突然获得推理能力。

先做受控诊断：

- 人类给正确大纲，模型能否写出合格正文？
- 人类给正确状态，模型是否仍制造矛盾？
- 正文合格时，模型自己的规划是否成为主要问题？

由此决定补数据、改训练还是改系统。不要同时增加大量模块，以致无法知道哪个改动有效。

## 12. 怎样证明“真的训练成功”

训练 loss 下降，说明模型更擅长训练目标；不能单独证明它会写好小说。不同 tokenizer、掩码和测试数据下的 loss 或困惑度，不宜直接排名。

建议设置三道门：

1. **工程门**：数据可追溯，训练数值正常，能存档、恢复和生成，恢复后的数据与配置没有意外改变。
2. **语言门**：在未见文本上验证；检查重复、乱码、句式和原文复现风险。
3. **故事门**：使用未进入训练的题目，让人读完整作品，评价逻辑、人物、推进、结局和可读性。

两条路线采用相同题目、长度范围和生成预算，隐藏模型身份并打乱顺序。报告每个维度、失败案例和多个题目的结果，避免只展示最好的一篇。模型评审可以辅助筛查，人类验收仍要真正阅读。

从零路线可以与简单基线以及自己不同训练阶段比较；微调路线至少要与未微调基座比较。已有基座的历史语料通常不完全可知，因此只能控制自己新增训练的泄漏，不能轻易保证基座从未见过某篇公开测试文本。

## 13. 对当前项目的判断

**“必须随机初始化”是明确的研究约束，30M 是合理的可运行实验起点；能否成为令人满意的独立小说作者，仍是需要验证的目标。** 如果未来评价标准变成“尽快得到成熟写作能力”，微调路线通常更有起点优势。这是目标差异，不意味着现在应该擅自切换路线。

截至本次文件核对，`py/novellm/model.py` 和 `py/novellm/trainer.py` 已经存在。`t30m` 配置采用 d=512、8 层、8 头、1024 上下文，实际参数量随词表变化。当前模型复用 MiniLM 的 LayerNorm、GELU 和可学习绝对位置编码，并非规划中的全部新架构都已落地。

训练器代码已包含分片数据读取、梯度累计、验证以及中断/限时存档等路径。**这是代码存在的证据，本次没有在目标 GPU 上跑正式训练，也没有据此宣称恢复正确性或小说质量已经验收。** 旧文档中 `py.novellm.train` 之类名称不能因为新增 `trainer.py` 就视为已经可用。

当前优先级应是：冻结一版完整数据清单与 tokenizer → 跑通小规模训练、恢复和生成 → 在目标 GPU 测吞吐与显存 → 按预算正式预训练 → 建立短故事 SFT 与盲评。模型架构是否换成更新设计，应通过同预算对照决定；不必把每种新技术都作为第一次正式训练的前置条件。

可以先让 30M 在有限题材、固定长度、明确结局的任务上过关，再逐步增加难度。若多轮有控制的实验仍明显受容量限制，再依据数据和成本决定扩大规模，而不是把训练时长无限加上去。

## 14. 其他路径及其与“从零”的关系

| 路径 | 做法 | 与当前要求的关系 |
|---|---|---|
| 从零预训练后 SFT | 自己训出的基座继续学任务 | 符合随机初始化主线 |
| 已有基座继续预训练后 SFT | 先适应小说语料，再学任务 | 继承外部权重，不符合当前硬要求 |
| 蒸馏或合成数据训练 | 用强模型的输出或软标签教小模型 | 学生可随机初始化，但数据依赖教师，须清楚披露 |
| 仅提示词与检索 | 不改权重，在输入里提供大纲和资料 | 是应用方案，不是从零训练 |
| 模型训练加写作系统 | 模型负责写作，外部程序管理计划与状态 | 两条训练路线都能结合 |

对教学和研究文章而言，从零路线的优势是过程可解释、实验可复现。文章应分别报告工程完成、语言改善和人类故事评价，保留失败样本，读者才知道结果的真实边界。

## 15. 推荐阅读顺序与案例

1. 先读本项目的[从零训练入门指南](NOVEL_MODEL_FROM_ZERO_BEGINNER_GUIDE.md)，理解数据到模型的流程。
2. 看 [nanoGPT](https://github.com/karpathy/nanoGPT)：理解小型自回归模型如何训练、保存和生成。它是训练工程参考，不是完整小说产品。
3. 读 [TinyStories](https://arxiv.org/abs/2305.07759)：了解受限故事数据与小模型能力的研究。其英语、受控语料条件不能直接推成“30M 一定能写中文长篇”。
4. 看 [LlamaFactory](https://github.com/hiyouga/LlamaFactory) 和 [TRL SFT](https://huggingface.co/docs/trl/main/en/sft_trainer)：理解微调任务如何组织，重点观察数据格式与训练配置。
5. 再读 [LoRA 官方解释](https://huggingface.co/docs/peft/main/en/conceptual_guides/lora)、[QLoRA 论文](https://arxiv.org/abs/2305.14314)与[显存构成](https://huggingface.co/docs/transformers/main/en/model_memory_anatomy)，理解显存为何减少、哪些开销仍存在。
