# 词表从 201 涨到 6,379，参数去了哪里

**系列：从零训练中文小说模型｜第 26 篇（实践篇·模型拆解课）**
**前置阅读：原理篇 2（字怎么变成数字：词表、OOV 与 UNK）、原理篇 3（字的向量：embedding）**

实验身份：model=MiniLM-char-v1｜cfg=ctx=32 d=40 layers=2 heads=4 ffMul=4｜词表按语料构建（min_freq=3）｜数据=5 桶公版语料（2,682 万字）

我一直用「5.5 万参数的小模型」介绍这个项目。直到把配置拆开算了一遍，才发现这句话**只对最开始那三段手写语料成立**。

## 一张表看清参数去向

先记住一个拆分：`d=40 layers=2` 的 Transformer **主体**（多头注意力 + FFN + 各层 LayerNorm，含位置表）恒为 **40,800** 个参数。它跟语料无关。剩下的全部来自词表：

| 语料 | 词表 V | 总参数 | 嵌入/输出表占比 |
|---|---:|---:|---:|
| 原始手写语料 | 201 | 48,840（≈「5.5 万」） | 16.5% |
| `story` 短故事 | 1,769 | 111,560 | 63.4% |
| `scifi` 科幻 | 3,741 | 190,440 | 78.6% |
| `wuxia` 武侠 | 5,182 | 248,080 | 83.6% |
| `gudian` 古典 | 6,379 | 295,960 | 86.2% |

这张表有一个可以手算验证的规律：

```text
总参数 = 40,800（主体） + V × 40（嵌入表）
```

- `scifi`：40,800 + 3,741 × 40 = 40,800 + 149,640 = **190,440** ✓
- `gudian`：40,800 + 6,379 × 40 = 40,800 + 255,160 = **295,960** ✓

从 201 个字的词表走到 6,379 个字，**Transformer 主体一个参数都没变**，涨的 25 万个参数全是那张查找表。到古典语料上，**86% 的参数在词表里，模型结构只占 14%。**

## 为什么会这样

因为嵌入层和输出层**权重共享**——同一张 `V × d` 的表，既负责「字 → 向量」，又负责「向量 → 各字的分数」。这是一个很划算的设计（省掉一整套输出矩阵），代价是**这张表必须同时承担输入和输出两种职责**，而且它的尺寸直接由词表决定。

于是语料越大、用字越杂，词表越胖，参数就越往表里堆。这也是为什么「这个模型多大」这个问题，**不看语料是答不出来的**。

## 词表变大，代价不止参数

| 代价 | 表现 |
|---|---|
| 参数量 | 每多 1 个字 +40 参数；从 201 到 6,379 多出约 24.7 万 |
| 稀疏与欠训练 | 罕见字出现次数少，它的行几乎学不到东西 |
| 未登录字 | `min_freq=3` 裁掉低频字 → 映射到 UNK（占留出切片 0.036%~0.72%） |
| 「小模型」的说法失真 | 同一个主体，在 `gudian` 上是 29.6 万参数的模型 |

最后一行值得单独说：本系列前面文章里的「5.5 万参数」，指的都是 201 字词表下的**那个**模型。**把语料换成公版全书后，它已经不是同一个规模的模型了——变的是词表，不是能力。**

## 那用子词（BPE）会不会省下来

直觉上是：词表 6,400 个 token 比 6,379 个字「大」，是不是更亏？

算一下：6,400 × 40 = **256,000**，比字符级的 255,160 只多 840 个参数——**表的大小几乎一样。** 真正的差别不在参数，而在**序列长度**：子词把长词压成一个 token，同样 32 的上下文能罩住更长的原文，等效上下文变长。

所以 BPE 的卖点不是省参数，是**在相同参数预算下换到更长的有效上下文**。至于它在中文小说上是否真的更好，得测，不能推。

**注意**：本项目目前的 BPE 只是一个 `num_merges=50` 的学习版（`py/tokenizer.py`，4 项断言通过），**并没有跑过 6,400 token 规模的对照**——上面那段是算式推导，不是实验结果。

**可复现入口**：`py/tokenizer.py` 的 `BPETokenizer`；参数账可直接按「总参数 = 40,800 + V × 40」手算核对。
