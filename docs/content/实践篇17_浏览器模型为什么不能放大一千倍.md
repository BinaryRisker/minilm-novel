# 放大模型前，先把数据、算力和内存算明白

> **小白先读（2026-09-17 修订）**：放大模型前先算数据、有效训练吞吐和完整内存；昵称和硬件峰值都不是训练预算。

浏览器实验台能训练一个小 Transformer，并不意味着改大层数就能得到成熟小说模型。先问三个实际问题：教材够不够合适，计算能否承受，效果怎样验收。

## 数据不是只看字数

一部书重复一百遍，会增加训练曝光，却不会增加一百部独立作品。主要是古典文风的语料，也不能自然代表现代短篇任务。扩大之前，应记录独立作品、去重家族、实际 token 数与来源用途，再准备独立验证作品。

“参数除以字数”可以描述规模，不是最优训练配比定律。当前项目曾从小语料扩大到百万字，但历史结果不能证明所有数据规模与模型配置已经充分训练。

## 时间用实际训练吞吐估算

本项目旧矩阵微基准记录 JS 0.56 GFLOPS、NumPy/OpenBLAS 69.2 GFLOPS。它只能说明那个环境与矩阵形状下的性能差，不能直接给出大模型训练时间，更不能推出固定租卡费用。

```text
估计训练秒数 = 计划曝光 token / 目标配置实测有效 token/s
总用时还要加：预处理、验证、存盘和任务间空闲
```

例如假设有效吞吐 5000 token/s，1 亿 token 约需 5.56 小时。这是算术示例，不是 GPU 测速结果。常见 6N FLOPs/token 也只是有条件的粗略计算量估算，不应拿微基准峰值直接除出交付日期。

## 内存不要漏掉梯度

以 5500 万参数、FP32、Adam 为简化例子，使用十进制 MB：

| 内容 | 近似大小 |
|---|---:|
| 权重 | 220 MB |
| 梯度 | 220 MB |
| Adam 的 m、v | 440 MB |
| 以上合计 | 880 MB |

这还没算激活、中间 logits、临时张量、缓存与框架开销。混合精度和分布式策略会改变账目，不能把这张表当峰值显存预测。

## 当前的实际模型是什么

`py/novellm/model.py` 的 t30m 是候选档名：d=512、8 层、8 头、ctx=1024、ffMul=4，复用 MiniLM 的学习式绝对位置、LayerNorm、GELU。它还不是旧设计手册中的 RoPE/RMSNorm/SwiGLU 模型。

实际参数量随词表变化。[GPU 交接记录](../HANDOFF_AUTODL_T30M_GPU_SMOKE_20260917.md)报告某次为 26,651,648 参数，并出现验证损失回升。它证明该配置跑通了一次短训练，不证明小说质量达标，也不是对所有数据的吞吐承诺。

新手先做 CPU 小练习；扩大时先核对数据与模型身份，再做目标机器短测，最后用验证曲线和完整故事决定是否增加预算。
