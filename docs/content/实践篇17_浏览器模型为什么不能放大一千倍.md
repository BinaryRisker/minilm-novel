# 浏览器里的训练模型为什么不能直接放大一千倍？

**系列：从零训练中文小说模型｜第 17 篇（实践篇·工程与性能）**
**前置阅读：原理篇 1（全景：一个小说模型有哪些零件）**

实验身份：model=MiniLM-char-v1（presets fast/std/deep/big）｜cost=按 GFLOPS 折算（估算）

「既然浏览器里能训 5.5 万参数，那把它放大一千倍不就成小 GPT 了？」

这个直觉会撞上三堵墙，而且第一堵不是算力。

## 墙一：语料，不是算力

现在三段语料各约 2000 字，模型 55,400 参数，已经约 **29 参数/字**。这个密度下模型的策略是背，不是学：训练损失能压到 1.3~1.6，留出集 NLL 却 3.5~5.7（实践篇第 10 篇）。

放大一千倍参数 = 5,500 万参数。要保持同样的「参数/字」密度不恶化，语料也得放大约一千倍，也就是**百万字级**。而按 `docs/DATA_CANDIDATES.md` 的实测结论：

> 「规模大 + 许可干净 + 故事边界清晰」这三个条件，目前中文小说数据里没有交集。

已抓到的 86 部公版作品、2472 万字，成分全是明清白话与晚清小说——模型会写「话说」「看官听说」，不会写现代小说。所以真正卡住的是**能训的现代中文小说语料**，不是 CPU。

## 墙二：算力量级

放一千倍，参数量与每 token 计算量同步放大。用常见估算口径（前向 + 反向 ≈ 6N FLOPs/token）算 100 万 token：

| 实现 | 实测吞吐 | 训 100 万 token（55M 参数）估算 |
|---|---|---|
| 手写 JS | 0.56 GFLOPS | ≈ 6.8 天 |
| NumPy / OpenBLAS | 69.2 GFLOPS | ≈ 1.3 小时 |

两者差 124 倍（实践篇第 12 篇：V8 不自动向量化成 AVX、JS 单线程、BLAS 有分块与预取）。也就是说，**同一个任务在浏览器里要跑一整周以上**，而它还不支持取消恢复、断点续训。

顺带一个内存账：float32 下 5,500 万参数是约 220 MB，加上 Adam 的两个状态向量就是三倍量级。浏览器标签页扛这个不合适。

## 墙三：放大之后，教学价值就没了

`index.html` 的全部意义是「看得见」：逐字 token 映射、损失曲线、训练快照、候选分布、注意力热力图，训练 400 步 1~2 分钟，拷到手机能跑。一旦放大，单次训练变成过夜任务，「改一个滑条立刻看到结果」就消失了。

所以项目的分工是固定的：**JS 版负责讲清每一步在算什么，PyTorch 版负责在真实算力上把它训出来**（`py/train.py`、`py/benchmark.py`，本机 N100 上单语料 400 步约 12~64 秒）。两套实现还做了 bitwise 对齐，对齐的是数学而不是规模。

## 真要放大，顺序应该是什么

1. 先把数据补齐（现代文风、许可干净），这是当前第一瓶颈；
2. 数据和步数到位后，再谈深度/宽度实验；
3. 如果扩到十万字级仍赢不了 trigram，那结论就要改写成「字符级小模型不适合中文小说」，转向基座 + SFT，而不是继续加参数。

## 顺手把内存账也算一遍

| 项目 | 5.5 万参数 | 5,500 万参数 |
|---|---:|---:|
| 权重（float32，4 B/参数） | ≈216 KB | ≈216 MB |
| + 梯度 | ≈432 KB | ≈432 MB |
| + Adam 两个状态向量 | ≈650 KB | ≈650 MB |
| + 激活值 / 缓存 | 随 batch 与 ctx 增长 | 同左，且更吃紧 |

所以「放大一千倍」在内存侧也是字面意义上的一千倍：**Adam 会额外存两份和参数一样大的向量**，这是很多人第一次训模型时显存爆掉的真正原因——不是权重太大，是优化器状态把账翻了三倍。

**可复现入口**：`index.html` 的预设档 `fast / std / deep / big`（big 也只在教学范围内：ctx=48、d=64、4 层、8 头、1000 步）；数据审计 `py/data/prepare.py`；吞吐 `py/benchmark.py`。
