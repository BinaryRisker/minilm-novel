# MiniLM Lab 内容扩展计划 V1

> **2026-09-17 阅读说明**：保留为历史内容规划，现行阅读与发布顺序见[阅读地图](README.md)，本轮逐篇处置见[文章审查](文章审查_2026-09-17.md)。

## 一、内容不要只围绕“模型今天写得怎么样”

这个项目有六种可以长期更新的素材：代码、数学、实验、失败、小说创作和读者参与。一次实现往往能拆成多篇文章，但每篇只回答一个问题。

例如“加入 tokenizer”可以拆成：

1. 为什么一个陌生字会消失；
2. 字符级 tokenizer 如何工作；
3. BPE 为什么要合并字节对；
4. 词表变大后参数去了哪里；
5. 两种 tokenizer 在中文小说提示词上的对照；
6. 这个改动有没有真正改善独立故事评测。

不要把这些文章合成一篇“全面介绍”。短文章负责吸引读者，长文章负责建立可信度，交互 demo 负责让读者留下来。

## 二、建议设置七个固定栏目

### 1. 模型拆解课

面向刚开始学大模型的人，用当前项目的可视化代码讲清一个组件。

- 一个字符怎样变成 embedding？
- 位置编码为什么存在？
- Q、K、V 到底在查什么？
- 因果 mask 如何防止偷看答案？
- 一个 attention head 和四个 head 有什么区别？
- LayerNorm 为什么放在残差之前？
- GELU 和 ReLU 改变了什么？
- 输出 logits 怎样变成下一个字的概率？
- 交叉熵为什么会惩罚“自信地猜错”？
- Adam 保存的两个状态分别做什么？
- 梯度裁剪为什么能防止训练爆掉？
- KV Cache 为什么能加速生成？

每篇固定包含一个数字例子、一张流程图和一个可在 `index.html` 里观察的现象。

### 2. 实验室周报

每次只改变一个变量，公布配置、命令、结果和失败样本。

- 训练 100、200、400、800 步，验证 loss 和生成变化；
- context length 从 8、16、32、64 的变化；
- embedding 宽度翻倍后是否真的更好；
- 1 层、2 层、4 层的收益和成本；
- batch size 与学习率的配对实验；
- 不同随机种子的结果波动；
- 字符级、BPE、字节回退的覆盖率比较；
- 纯原创语料与结构化语料的差异；
- 单一题材与混合题材的风格稳定性；
- 训练数据量从 500 字到万字的曲线；
- 模型容量和数据量哪个更值得先增加；
- 预训练、SFT、编排三者的消融实验。

标题尽量写成问题，例如“增加一倍参数，真的能少写一倍废话吗？”

### 3. 失败样本档案

这是最容易建立信任的栏目。每篇挑一个完整失败样本，不剪掉上下文，只加人工批注。

- 人物名字突然变化；
- 已经关上的门又被打开；
- 角色说了没有动机的话；
- 景物描写连续重复；
- 段落很漂亮，但冲突没有推进；
- 模型把多个训练片段缝在一起；
- 低温度复读，高温度失控；
- 语料外输入退回高频字先验；
- 长度增加后人物状态丢失；
- 大纲给得很清楚，模型仍然没有完成结尾。

每篇结尾回答：“这个失败更可能来自数据、模型容量、上下文、解码，还是评测方法？”

### 4. 小说工坊

把模型放进真实写作流程，而不是只展示自动续写。

- 人类先写人物卡，模型补充矛盾点；
- 人类提供三句话大纲，模型写一个场景；
- 同一场景让模型写三种文风；
- 让模型先写坏稿，再由人工逐句修订；
- 比较“直接写正文”和“先列事件再写正文”；
- 让模型维护人物状态表；
- 让读者投票决定下一章的冲突；
- 将读者投稿场景放入固定测试集；
- 一段人类原稿、模型续写和人工改稿的三栏对照；
- 记录一篇 800 字场景从草稿到终稿的全部修改。

这里的核心叙事不是“AI 替我写小说”，而是“模型在哪些步骤有用，在哪些步骤必须由人做决定”。

### 5. 工程与性能

这些内容可以吸引对底层实现感兴趣的读者，也能说明项目为什么保留 JS 教学版、另建 PyTorch 训练版。

- 手写矩阵乘法为什么比 OpenBLAS 慢 124 倍；
- 浏览器适合教学和推理，为什么不适合训练大模型；
- 一步训练到底花在哪里；
- 参数量、显存和优化器状态的账本；
- float32 梯度检查为什么会“假失败”；
- checkpoint 应该保存哪些状态；
- 随机种子为什么仍然不能保证所有环境逐位相同；
- 训练中插入一次生成，为什么可能污染后续实验；
- 如何让长任务支持取消和恢复；
- 如何把模型压缩到手机上运行；
- WebGPU 推理和浏览器训练的区别；
- 一次失败训练实际浪费了多少时间和钱。

### 6. 研究论文白话解读

每篇只讲一篇论文的一个观点，并明确区分“论文证明了什么”和“本项目还没有验证什么”。

- TinyStories：为什么受限数据能帮助小模型学会连贯故事；
- StoryWriter：为什么大纲、规划和动态上下文有用；
- 长文本生成中的 lost in the middle；
- DPO 与 GRPO 的训练目标差异；
- RoPE 与长上下文外推；
- 小模型的参数、数据和训练预算如何互相制约；
- 语言模型评测为什么不能只看 perplexity；
- 人类评测和 LLM-as-a-judge 各自的偏差。

文章固定使用三段：论文问题、论文结论、对 MiniLM Lab 的可检验实验。

### 7. 社区挑战

把读者从旁观者变成实验的一部分。

- 读者提交一句训练集外提示词；
- 读者猜哪段文字来自 trigram、哪段来自 Transformer；
- 读者给三个生成结果匿名评分；
- 读者提交一个人物卡；
- 读者找模型输出里的时间线矛盾；
- 读者投票下一次只改变哪个变量；
- 读者用同一 prompt 在手机上运行模型并回传结果；
- 读者提交失败样本，作者分析失败原因。

每次挑战都要公开规则、样本数量和截止时间，避免只挑选对项目有利的反馈。

## 三、可以直接使用的 30 个标题

1. 一个字是怎样穿过 Transformer 的？
2. 模型第一次学会的不是故事，而是标点
3. 为什么注意力热力图不能直接当作“模型思考过程”
4. 我把因果 mask 拿掉，模型会偷看答案吗？
5. 一个 attention head 到底在关注什么？
6. 训练 100 步、400 步和 800 步，故事发生了什么变化？
7. 5.5 万参数为什么会过拟合 2000 个字？
8. 我给模型更多上下文，它反而没有变聪明
9. 同一个 seed，为什么旧评测协议会得出不同成绩？
10. 三个随机种子就够了吗？我不再相信单次 benchmark
11. 字符级分词真的适合中文小说吗？
12. 词表从 300 个字扩到 6400 个 token，代价是什么？
13. 一个未知字被替换后，模型还算理解原句吗？
14. BPE 合并的不是词，而是一组统计上常见的片段
15. 数据从 500 字增加到 2400 字，为什么还赢不了 trigram？
16. 让模型写同一场戏三次，哪一次最像人写的？
17. 人物卡真的能防止角色性格漂移吗？
18. 先写大纲再写正文，是否真的更连贯？
19. 模型会写漂亮句子，但不会让人物做决定
20. 最像小说的失败样本，往往不是乱码
21. 我如何给一段 AI 小说做“事实检查”
22. 训练集重合率接近 0%，为什么仍然不代表原创？
23. 浏览器里的训练模型为什么不能直接放大一千倍？
24. 124 倍性能差距，究竟来自 JS 的哪一层？
25. float32 让我以为反向传播写错了

28. 一次实验应该公开哪些数字？
29. 如果简单基线赢了，项目还值得继续吗？
30. 我们到底是在训练模型，还是在训练自己的实验习惯？

## 四、推荐的文章结构

### 短文：800～1200 字

适合平台首发和短视频图文说明：

1. 一个反直觉开头；
2. 一个最小实验；
3. 一张表或一段输出；
4. 一个失败或限制；
5. 下一次实验预告；
6. 一个让读者可以亲自尝试的问题。

### 长文：2000～4000 字

适合周报或专栏：

1. 问题和假设；
2. 实验设置与唯一变量；
3. 结果表；
4. 原始样本；
5. 与简单基线的比较；
6. 失败原因和替代解释；
7. 结论边界；
8. 可复现命令；
9. 下一轮实验。

### 短视频或图文卡片：30～90 秒

只讲一个瞬间：

- 输入一句话，展示 OOV token；
- loss 从乱码降到成句；
- 模型和 trigram 同时预测一个字；
- JS 与 PyTorch 的数值对齐；
- 一段“很美但没有故事”的失败输出。

结尾固定放项目链接和完整实验报告，而不是只放结论。

## 五、每次代码改动如何自动拆成内容

一个功能至少产出以下四类材料：

| 产物 | 内容 | 例子 |
|---|---|---|
| 教程 | 解释原理 | 为什么增加随机流 |
| 实验 | 展示数字 | 有无独立 RNG 的差异 |
| 失败复盘 | 讲错误 | 生成污染后续训练 |
| 体验内容 | 让读者操作 | 读者输入陌生字看 token |

不要等模型有“大突破”才发文。小模型项目最有价值的内容往往是“一个假设被数据推翻”。

## 六、推荐发布节奏

每周围绕一个主题发布三种长度：

- 周一：一个问题的短文或短视频；
- 周三：交互截图、数据卡或失败样本；
- 周末：完整实验报告和复现命令。

四周主题可以这样排：

| 周次 | 主线 | 长文 | 配套短内容 |
|---|---|---|---|
| 第 1 周 | 输入透明 | OOV 与 tokenizer | 逐字 token 动画、陌生字挑战 |
| 第 2 周 | 评测诚实 | Transformer vs trigram | 盲猜模型、基线数据卡 |
| 第 3 周 | 实现可信 | JS 与 PyTorch 对齐 | 梯度检查、Adam 单步动画 |
| 第 4 周 | 小说能力 | 很美的废话与场景实验 | 失败样本、读者盲评 |

完成一轮后，根据“有效评论、复现次数、交互完成率和复访”调整栏目。播放量可以记录，但不能单独作为内容质量指标。

## 七、发布前检查

- 是否写明模型版本、语料字数、seed、步数和评测协议？
- 是否有一个简单基线，而不是只有随机猜测？
- 是否保留至少一个完整失败样本？
- 是否区分训练集表现和独立测试表现？
- 是否把推测写成了结论？
- 是否能给读者一个实际可操作的入口？
- 是否注明生成内容来自自研模型、基座模型，还是人工改写？

内容的长期价值来自可追溯和可复现。项目越诚实，后续每一次改善越有说服力。
