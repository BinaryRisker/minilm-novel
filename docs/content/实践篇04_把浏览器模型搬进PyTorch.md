# 把浏览器里的模型搬进 PyTorch：我怎么确认没有写错

**系列：从零训练中文小说模型｜第 4 篇（实践篇）**
**前置阅读：原理篇 1（全景：一个小说模型有哪些零件）**

实验身份：model=MiniLM-char-v1(PyTorch 复刻)｜cfg=ctx=4 d=8 layers=1 heads=2 ffMul=2｜V=9｜precision=float64

我在浏览器里手写了一个 Transformer。下一步要用 PyTorch 训练更大的数据，但“重新写一遍代码、跑出相似曲线”并不能证明两份实现相同。

所以我没有先训练，而是先让两份代码共享同一组权重、输入和目标，逐项比较结果。

## 对齐了哪些东西

小配置使用 `ctx=4、d=8、1 层、2 个注意力头、9 个字符`。从 JavaScript 导出权重后，PyTorch 依次核对：

- 前向 logits 和 loss；
- 每个参数的原始梯度；
- 梯度裁剪后的结果；
- Adam 更新后每个参数的新值。

结果是：logits 最大误差 `5.55e-17`，原始梯度误差不超过 `1.94e-16`，Adam 更新误差不超过 `4.68e-17`。
逐项写成表是这样：

| 检查项 | 最大误差 | 结论 |
|---|---:|---|
| 前向 logits | 5.55e-17 | 逐位一致 |
| 前向 loss | 9.02e-09 | 差异来自 JS 端 log 加了 1e-9 的 epsilon |
| 原始梯度（20 个参数） | ≤ 1.94e-16 | 逐位一致 |
| 梯度裁剪后（20 个参数） | ≤ 1.94e-16 | 逐位一致 |
| Adam 单步后（20 个参数） | ≤ 4.68e-17 | 逐位一致 |


也就是说，在 float64 的这个最小算例里，两边不是“差不多”，而是逐项对齐。

## 中间仍然失败过

第一次验证时，我看到 embedding 梯度差了 0.28，以为反向传播出了 bug。后来发现是验证脚本把参数值当成了梯度读取。

Adam 也出现过误差。手写公式和 PyTorch 的运算顺序略有不同，导致部分参数差异达到 1e-2。最终改为使用 PyTorch 优化器真实执行一步，并严格匹配 JS 端的梯度裁剪顺序。

这两个错误都很普通，但如果只看最终生成结果，很难知道问题来自数学实现、优化器，还是随机种子。

## 这一步为什么值得公开

“我训练出了一个模型”不如“我能证明实现的每一步是什么”有说服力。对齐测试也让我获得了一条安全的学习路径：以后改分词、改 RoPE、改 SwiGLU 时，每一次变化都可以先在小算例上验证，再进行昂贵训练。

当然，这还不代表长期训练曲线一定逐位相同。两边的随机数生成器不同，独立训练只比较趋势和统计波动。数学对齐和训练结果对齐，是两个问题。

## 对齐了数学，没对齐随机数

有一个边界必须写清楚：**两边的随机流没有对齐。** JS 用 mulberry32，PyTorch 用 MT19937，这是两套完全不同的生成器。所以即便每一步的数学逐位相同，各自独立训练出来的模型也不会一样。

这不是偷懒，而是刻意的分工：

| 问题 | 靠什么回答 |
|---|---|
| 「两份实现是不是同一个模型」 | 固定输入下的 bitwise 对齐（本篇） |
| 「两份实现训出来的模型是不是同一个东西」 | 多种子的分布对比（均值差 ≤ 2×σ_pool） |

第一个问题在 5.5 万参数、3 分钟训练的成本下就能排查干净；第二个问题才需要跑多个种子。这也是为什么 L0（平移验证）排在扩数据前面——**等语料上到百万字、开始租卡之后才发现评测链路有 bug，代价就是真金白银。**
