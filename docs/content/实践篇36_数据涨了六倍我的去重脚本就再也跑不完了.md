# 数据变大以后，去重脚本为什么跑不完

> **小白先读（2026-09-17 修订）**：大规模去重需要候选索引与复核；修复结果必须绑定数据快照，不能把旧清单当现行证据。

**系列：从零训练中文小说模型｜第 36 篇（实践篇）**

一开始只有几十部作品，逐对比较还能完成。后来增加到十几万部，“把旧算法再跑一遍”就变成了工程问题。

## 先算要比较多少对

55 部作品有 `55×54/2=1485` 对；191679 部约有 183.7 亿对。工作量按作品数的平方增长，不能只按文件数增长倍数估时间。

历史记录中 22 秒是锚点方法的小桶整体耗时，1.25 秒/对是另一种全文精确复核路径。两种时间不能混在一起当成同一个算法的测速。按后者外推约数百年，只能表达朴素方法不可行，不能当成实际测得的运行时间。

## 倒排索引怎样减少候选

把每行文字做指纹，记录“这行在哪些作品里出现”。只有共享行的作品才进入候选对，不再盲目比较所有作品。历史 localugc 快照有约 338 万个去重行指纹，记录耗时约 156 秒；这是该快照和机器下的观测。

代价是整行匹配可能漏掉不同断行的同书异本。小桶可用与断行无关的内容锚点，候选再用原文精确复核。索引查到的相似也可能是版权模板、分隔线，不能直接认定同源。

| 问题 | 应对 | 仍需注意 |
|---|---|---|
| 公共模板制造相似 | 过滤过于常见的行或锚点 | 阈值可能误删真实关系 |
| 极短作品重合比例不稳定 | 设最小共享量并精确复核 | 不同长度作品需要诊断 |
| 同书断行不同 | 内容锚点补充候选 | 候选生成仍可能漏检 |
| A 连 B、B 连 C 形成大簇 | 审核边及簇成员 | 连通不等于每两部都强相似 |

## 阈值改了，为什么“簇数”没变

历史小桶扫描发现，精确复核阈值 0.02 漏掉了重合约 0.0159 的真实关系。改成 0.005 后它被纳入，但跨 split 簇总数仍可能是 3，因为变的是簇成员。

所以不仅要对比“有几个簇”，还要对比哪些作品移动、哪些留出片段仍命中。该阈值只在这批候选上得到支持，不是全库通用最优值。

## 修复必须绑定数据版本

旧 v3 产物对应 192823 部快照，后来主清单换成 225756 部。文件名叫 v3 并不意味着它仍能用于新语料；必须核对作品集合、正文指纹和切分身份。

历史记录显示六个小桶的相关抽样检查通过，但 localugc 的文本级漏检不能由此排除。当前默认入口选择哪个清单，必须查看 `splits.resolve_current()` 与实际报告。正文、清单或阈值改变后，旧零命中不能沿用为新成绩。
