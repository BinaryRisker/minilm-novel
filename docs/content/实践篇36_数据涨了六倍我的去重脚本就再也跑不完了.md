# 数据涨了六倍，我的去重脚本就再也跑不完了

**系列：从零训练中文小说模型｜第 36 篇（实践篇·实验室周报）**
**前置阅读：实践篇 34（按作品切分就够了吗？古书里有异名同书和选本）、实践篇 33（续训后 loss 更低不代表续训是对的）**

实验身份：buckets=gudian/wuxia/urban/xiandai/scifi/story/localugc（全 7 桶）｜语料=按作品整篇切分（指纹 `ba915011fd4ce482`，192,823 部 / 2.43 亿字）｜协议=小桶走锚点法（winnowing，对齐无关）、大桶走行级倒排索引，行级三道守卫 + 锚点两道守卫，簇级并查集重切分

第 34 篇结尾我留了一句话：**「只查了 gudian / wuxia / urban 三个桶，story / scifi / xiandai / localugc 没查」**。这一轮把这句话补完。

补的过程里，最值得写的不是「查完了」，而是**我的方法在三处失效、两处假阳性、还有一处我自己新加的守卫制造了一个新漏检**。下面按踩坑顺序记。

## 失败样本 1：算法直接跑不完

第 34 篇的 `py/dedup_works.py` 是**全量两两比对**：每桶 n 部作品 → C(n,2) 对，每对算一次锚点重叠。

写它的时候 gudian 有 55 部，C(55,2) = **1,485 对**，跑了 22 秒。我当时觉得这个算法没问题。

这一轮数据是 192,823 部，其中 `localugc` 一桶 **191,679 部**。C(191,679,2) ≈ **1.8×10¹⁰ 对**。按第 34 篇实测的 1.25 秒/对，需要 **700 年**。

数据规模变了，**算法必须换，不是优化**。换法：论坛帖的天然单位是「行」（一楼/一条回复），建**行指纹 → 作品**的倒排索引：

| | 单位数 | 说明 |
|---|---|---|
| 全量两两比对 | 1.8×10¹⁰ 对 | 每对都要算一次重叠 |
| 行级倒排索引 | **3,382,869** 个去重行指纹 | 只遍历一次所有行，共享行的作品才成为候选对 |

单位数少了 **5,400 倍**（差四个数量级）。localugc 实测 **156 秒**跑完。

## 失败样本 2：行级法漏掉「同书异本」

换成行级法之后，gudian 报出来的簇从 3 个变成 2 个——**《三国志演义》和《三国演义》不见了**。

原因很直白：行指纹要求**整行逐字相同**。两个版本的断行位置不同，《三国演义》里的一行在《三国志演义》里被切成两行，于是**没有一行指纹是相同的**，行级法完全看不见它们。而它们的内容锚点重合度是 **0.5516**、精确复核 **0.3693**——同一个故事的两个版本。

所以最终做法是**分层**：作品数 ≤ 3,000 的桶走锚点法（对齐无关，抓得住同书异本），否则走行级倒排（可扩展，但漏断行不同的版本）。

| 桶 | 作品数 | 走哪条路 | 跨 split 簇 |
|---|---|---|---|
| gudian | 55 | 锚点法 | **3** |
| wuxia | 23 | 锚点法 | 0 |
| urban | 26 | 锚点法 | 0 |
| xiandai | 35 | 锚点法 | 0 |
| scifi | 5 | 锚点法 | 0 |
| story | 1,000 | 锚点法 | 0 |
| **localugc** | **191,679** | **行级倒排** | **295** |

合计 **298 个跨 split 簇**——留出集里确实还有东西。

## 失败样本 3、4、5：三道假阳性

数字大不等于对。三处假阳性，各自暴露一个守卫的缺失：

**(3) 分隔线撑起了比例。** `localugc` 里排在最前的是几部 300 万字级巨型天涯长帖，它们互相「共享」的只有 `—`、`-----` 这类分隔线。但它们的行数巨大，`共享行数 / min(行数)` 这个比例被分母放大到看似合格。修法：加**最少共享字数**守卫（200 字），并且 **containment 改按字数算**而不是按行数算。

**(4) 短作品的锚点集太小。** story 桶报出 10 个「簇」，但逐字精确复核**全部是 0.0**。作品字数中位数只有 253 字，20 字的 k-gram 根本没几个锚点，重叠纯属统计噪声。修法：加**精确复核门槛**（`--min-exact`），锚点重叠再高也要逐字查得出来才算同源。story 的 16 对候选全部被挡掉 → 0 簇。

**(5) 版权声明模板。** xiandai 桶的 wikisource 来源有一批作品共享同一段版权声明模板，让 11 部作品「锚点重叠 0.125、精确复核 0.143」。修法：加**锚点 df 过滤**（出现在太多作品里的锚点先剔掉），只这一道就剔掉 388 个模板锚点 → 0 簇。

五道守卫（行级三道 + 锚点两道）补齐后，六个小桶的跨 split 簇**全部归零**，只有 gudian 保留 3 个真簇（含被行级法漏掉的《三国演义》对）。

## 修复前后：12.00% → 0.00%

用 `py/audit_splits.py` 的 B 组检查（从 val/test 随机抽 150 个 40 字片段，逐段在 train 全文里精确查找）对照：

| 桶 | 检查 | 修复前 | 修复后 |
|---|---|---|---|
| gudian | val 片段能在 train 找到 | **18/150（12.00%）** | **0/150（0.00%）** |
| gudian | test 片段能在 train 找到 | **22/150（14.67%）** | **3/150（2.00%）** |
| xiandai | val / test | 0/150、0/150 | 0/150、0/150 |
| story | val / test | 0/150、0/150 | 0/150、0/150 |

切分从 44/5/6 变成 **47/4/4**，全库移动 **427 部**（665 个簇），新清单指纹 `901a6a299d899fb6`。

逐部作品归因看得更清楚（300 探针/部）：

| 留出作品 | 修复前命中 | 归属 train 作品 | 修复后 |
|---|---|---|---|
| 《新齐谐》 | **127/300（42.33%）** | 《子不语》 | 已移入 train |
| 《三国演义》 | **100/300（33.33%）** | 《三国志演义》 | 已移入 train |
| 《警世通言》 | 20/300（6.67%） | 《今古奇观》 | 已移入 train |
| 《二刻拍案惊奇》 | 7/300（2.33%） | 《初刻拍案惊奇》4 次、《今古奇观》3 次 | **仍在 test，命中不变** |

《新齐谐》42.33%——**每 2.4 个片段就有 1 个能在训练集里逐字找到**，而它当时被判为「干净的留出集」。这就是纯按作品切分的漏检规模（作品级切分的口径来源见 `docs/experiments/2026-09-14-worksplit-nll-converge.md`）。

## 失败样本 6：残余的 2.00%，是我自己的新守卫造成的

上表最后一行就是这一轮**没修掉**的部分：`gudian/test` 还剩 3/150。

顺着探针片段反查，源头唯一：**《二刻拍案惊奇》（test）** 与 train 里的《初刻拍案惊奇》《今古奇观》有 1%~2% 的重合。

我去看这两对的原始数字，发现根因不是阈值，而是我这一轮**为了修 story 假阳性而新加的 `--min-exact` 守卫**：

| 对 | 锚点重合 | 精确复核 | 是否进簇 |
|---|---|---|---|
| 《今古奇观》(train) ↔ 《警世通言》(test) | 0.1351 | 0.0584 | 进（真泄漏） |
| 《今古奇观》(train) ↔ 《二刻拍案惊奇》(test) | **0.0519** | **0.0159** | **不进** |
| 《初刻拍案惊奇》(train) ↔ 《二刻拍案惊奇》(test) | 0.0102 | 0.0080 | 不进 |

看第二行：锚点重合 **0.0519 已经过了 0.05 的判定线**，但精确复核 0.0159 差一点点没到 0.02 的门槛，于是被判成噪声剔掉。而上面 story 桶那 16 对噪声的精确复核是 **0.0**——**门槛从 0 挪到 0.02 是为了挡住 0.0，结果一并挡住了 0.0159 的真泄漏。**

`exact_containment` 本身是可复现的（等差 stride 采样，用 `random` 就会变成抽签），所以这不是抖动，是**门槛压在了决策边界上**：真实重合约 1%~2%，而门槛是 2%。

我把这个结论端到端验证了一遍：gudian 单独跑 `--min-exact 0`，这两对进了簇，gudian 变成 **48/4/3**，B 组检查 **val 0/150、test 0/150，门禁通过**（退出码 0）——正好回到第 34 篇 v2 修完的状态。

**但我没有把默认值改成 0。** 0.005~0.019 这段区间里还有多少真泄漏、多少假阳性，我只有 gudian 一个桶的两个数据点，没有资格拍这个数。这属于「知道在哪、还不知道该设多少」。

| 配置 | gudian 切分 | val 泄漏 | test 泄漏 | 门禁 |
|---|---|---|---|---|
| v1（修复前） | 44/5/6 | 18/150（12.00%） | 22/150（14.67%） | 失败 |
| **v3（本轮默认，`min-exact 0.02`）** | **47/4/4** | **0/150（0.00%）** | **3/150（2.00%）** | **失败** |
| v3'（`min-exact 0`，仅诊断） | 48/4/3 | 0/150（0.00%） | 0/150（0.00%） | 通过 |

## 失败样本 7：并查集把弱边串成了大簇

最大的 localugc 簇有 **232 部**作品。我去核对第一部与第二部的直接关系：

```
localugc_001 与 localugc_002 之间没有直接边
路径：001 --(cont=0.3684)-- localugc_3543 --(cont=0.0806)-- localugc_002
002 的直接邻居只有 1 个：localugc_3543（cont=0.0806）
```

「A 和 B 同源、B 和 C 同源」被我直接当成了「A 和 C 同源」——**并查集的传递性，不是同源关系的性质**。232 部那个簇里 930 条边，只有 **122 条**是强边（cont ≥ 0.3），剩下 808 条是弱边铺的路。全库 662 个簇里，**111 个连一条强边都没有**。

不过这件事有两面，不能只写坏的一面。3,865 条过阈值边的重合度分布是：

| 分位 | p10 | p25 | p50 | p75 |
|---|---|---|---|---|
| cont | 0.076 | 0.172 | **0.644** | 0.911 |

**过半数的边重合度在 0.64 以上**，440 条边是 0.999 以上（几乎是同一篇）。也就是说**大多数簇是真的密集团**，链式放大集中在少数枢纽作品上（`localugc_001` 一个节点就有 61 个邻居，它是一部 324 万字的巨型聚合帖）。

而且放大方向的代价很小：全库移动 427 部，占 **0.22%**；localugc 的留出集从 38,336 部变成 37,918 部，缩了 1.09%。**多合并只是把留出集缩小，不会把训练集见过的文本留在留出集里**，所以我保留了当前行为，把「用枢纽法替换传递闭包」写成下一步而不是这一轮硬改。

## 失败样本 8：清单凭空大了 15 MB，而我把理由也说错了

`resplit()` 产出的 v3 清单是 **104,786,999 字节**，比 v1 的 88,763,025 字节大了 **15.28 MiB（+18%）**——而两者作品数完全相同（192,823 部）。我去做了逐字节归因：

| 新增字段 | 字节 | 字节/行 |
|---|---|---|
| `dedup_cluster` | 6,631,877 | 34.4 |
| `dedup_cluster_size` | 4,627,752 | 24.0 |
| `orig_split` | 4,184,886 | 21.7 |
| **合计** | **15,444,515（占增量的 96.4%）** | |

原因是我在 `resplit()` 里**无条件给每一行**都补了这三个溯源字段。但：

- 真正换了 split 的作品只有 **427 部（0.22%）**
- 真正在 ≥2 部簇里的作品只有 **2,193 部（1.14%）**
- 其余 **99% 的行**里，`dedup_cluster` 恒等于**它自己的 story_id**、`dedup_cluster_size` 恒为 **1**——**零信息量**

改成「只在有信息量时写」之后：

| | 字节 | MiB |
|---|---|---|
| v1 | 88,763,025 | 84.65 |
| v3（无条件补字段） | 104,786,999 | 99.93 |
| **v3（只在有信息量时写）** | **88,904,420** | **84.79** |

比 v1 只大 **141 KB（+0.16%）**，切分指纹完全不变（仍是 `901a6a299d899fb6`），因为指纹只由 `(story_id, 内容哈希, split)` 决定。

**而我把理由也说错了。** 初版我写的是「105 MB 超过 GitHub 100 MB 单文件上限所以不入库」。查了 GitHub 官方文档才发现：硬上限是 **100 MiB（104,857,600 字节）**，那份 104,786,999 字节的文件其实**擦线通过，只差 69 KB**。数字看着像超了，是因为我拿 100 MB（10⁶）当成了上限，而且 99.93 MiB 在终端里显示成「104.79 MB」——**两次单位混淆叠在一起，就造出了一个不存在的事实**。

这个错误有代价：另一条工作流写了一个 `splits.resolve_current()`，按「哪一代去重产物有完整文件落盘」自动择优；它照着我的错误结论把 v3 判定为「超限没落盘」而回退到 **v1 + 告警**——**「修复不回流」这件事被我自己的一块错误招牌挡住了。**

修完字段后 v3 = 84.79 MiB（距上限 15.21 MiB），完整文件落盘入库，`resolve_current()` 现在自动选中 v3，实测：

```
resolve_current -> manifest: manifest_v3.jsonl
                   report  : split_report_v3.json
```

教训比数字值钱：**「超限」这类可查证的外部约束必须查证，不能靠数量级直觉；MiB 和 MB 差 4.9%，而在 99.93 这个位置上，4.9% 正好决定了「做不做得到」。**

## 顺手记：上一轮的修复悄悄回退了

第 34 篇把 gudian 修成 48/4/3。这一轮开跑前我先量了一次现状：**gudian 又变成 44/5/6，val/test 泄漏 12.00% / 14.67%——和第 34 篇修复前逐字相同。**

原因不是修复无效，而是**修复只落在旁支文件 `data/manifest_v2.jsonl` 里**：主清单 `data/manifest.jsonl` 后来被数据管线重新生成，v2 的簇级切分没有回流，于是整条修复被丢掉了。

这次我改了两件事：产出 `data/manifest_v3.jsonl`（与 v1、v2 同级，不覆盖任何旧文件），并且**所有数字锚定在 manifest 快照指纹 `ba915011fd4ce482`（192,823 部）**——跑的时候数据管线仍在被另一条工作流重写，不用快照数字会漂。

## 边界

- **`gudian/test` 仍有 2.00% 残余**，本轮的判定是门禁**失败**，不是通过。残余来源已定位到《二刻拍案惊奇》，修它的旋钮也找到了（`--min-exact`），但我没有改默认值——改它需要敏感性扫描，而不是两个数据点。
- **localugc 没有跑 B 组文本级探针**：它的 train 有 1.9 亿字，`片段 in 全文` 每次都是线性扫描，150 个探针不可行。localugc 的证据是**作品级**的（行级倒排：588,232 个共享行候选对 → 三道守卫后剩 3,865 对 → 逐对精确复核），与 gudian 的片段级证据不同口径，不能直接比。
- **行级法漏「断行不同」是已知缺陷**，它正是 localugc 走的路径。我在 localugc 上**没有**独立手段证明没有漏检——只能说在「整行逐字相同」这个口径下扫了一遍。
- **链式放大 111 个簇没有人工逐簇核对**，我只核了最大的 2 个。`cont ≥ 0.3` 这个「强边」定义是我拍的。
- 阈值 0.05、最少共享 200 字、df 上限 200、`--min-exact 0.02` 全部是拍的；这一轮**只对 gudian 做了小规模阈值扫描**，其他桶没扫。
- 427 部移动后，`scifi` 的 test 只剩 1 部、gudian 的 test 4 部——留出集更小、方差更大，跨档位比较时要记住。
