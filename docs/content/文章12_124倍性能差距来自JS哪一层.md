# 124 倍性能差距，究竟来自 JS 的哪一层？

**系列：从零训练中文小说模型｜第 12 篇（工程与性能）**

实验身份：env=Intel N100 / Node 单线程｜bench=dev/bench.js 矩阵微基准｜对比=NumPy/OpenBLAS

同一块 CPU（Intel N100），同一个矩阵乘法：

- 我手写的 JS 版本：约 **0.56 GFLOPS**
- NumPy / OpenBLAS：**69.2 GFLOPS**

差了 **124 倍**。这不是「JS 慢一点」，是差了两个数量级。
| 实测项 | 数值 | 环境 |
|---|---:|---|
| 手写 JS 矩阵乘 | 0.56 GFLOPS | Node 单线程，Intel N100 |
| NumPy / OpenBLAS | 69.2 GFLOPS | 同机 |
| PyTorch 训练吞吐 | 10,866 tokens/s（23.6 ms/step） | 同机，scifi 400 步 |

前两个数就是那个 124 倍的来源；第三个是「换到 Python 之后真实训练能跑多快」。


## 为什么差这么多

拆开看，差距主要来自三层，不是某一条慢代码：

1. **V8 不会自动向量化成 AVX。** 手写 JS 是标量循环，一次算一个数；BLAS 用 SIMD 一条指令并行算多个。这是最大的一块差距来源。
2. **JS 单线程。** 我们的教学版跑在 Node 单线程上，没用 Worker 并行；BLAS 会吃满多核。
3. **BLAS 有分块、寄存器累加、预取。** 矩阵乘不是「三层 for 循环」那么朴素——分块让数据留在 cache，寄存器累加减少内存往返，预取掩盖访存延迟。手写版这些都没有。

换句话说，这个基准中的主要差距来自实现路径：我用了朴素的标量循环，对方用了几十年沉淀的数值库。它不能证明所有 JavaScript 都比所有数值库慢，也不能把这个矩阵基准直接当成完整训练速度。

## 那浏览器里的模型还有意义吗

有，但分工要清楚：

- **浏览器 / JS 版**：负责教学和交互。读者能亲眼看着随机数字变成中文句子，零安装、能拷到手机跑（`index.html`）。这一步的价值是「可玩、不可转述」。
- **真实训练**：走 Python / PyTorch。本机 N100 上 PyTorch 单语料 400 步约 12~64 秒，是 JS 版的 3~18 倍；而 `benchmark.py` 测到吞吐约 **10,866 tokens/s、23.6 ms/step**。

结论很朴素：**浏览器适合教原理和做推理演示，不适合训练大模型。** 把训练塞进浏览器，是拿最慢的那把尺子去量最重的活。

## 同一个模型，三种跑法

差距不是抽象的「快一点」，落到具体数字是：

| 跑法 | 速度 | 环境 |
|---|---|---|
| 手写 JS 训练 | 3.9 step/s（scifi 400 步 103.7 秒） | Node 单线程，Intel N100 |
| PyTorch 训练 | 400 步 12~64 秒 | 同机，约 3~18 倍 |
| PyTorch 吞吐 | 10,866 tokens/s、23.6 ms/step | 同机，CPU |

注意第二行的 3~18 倍，和矩阵微基准的 124 倍不是一回事：**端到端训练里混着数据切片、采样、评测这些不是矩阵乘的部分**，所以整体提速必然小于纯矩阵乘的差距。引用倍数时，一定要说清它来自哪一层。

## 这件事的延伸价值

它也是为什么项目保留了两个版本：JS 教学版讲清「Transformer 每一步在算什么」，PyTorch 版讲清「怎么在真实算力上把它训出来」。两套实现还做了 bitwise 对齐验证（见选题 4）——对齐的正是数学，不是性能。

**可复现入口**：JS 教学版 `minilm.js` + `index.html`；Python 训练与吞吐见 `py/benchmark.py`。
