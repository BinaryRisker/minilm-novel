# float32 让我以为反向传播写错了

**系列：从零训练中文小说模型｜第 13 篇（工程与性能）**

实验身份：gradcheck cfg=ctx=8 d=8 layers=1 heads=2 ffMul=2 B=2 T=8 eps=1e-5｜float32 vs float64

做梯度检查时，我一度以为自己把反向传播写错了。

## 800 多个分量「不通过」

梯度检查的标准做法是：对每个参数，用有限差分算数值梯度，和反向传播算的解析梯度比相对误差，误差大于阈值就判 FAIL。

在 **float32** 下，我手写 JS 实现的 800+ 个梯度分量，大量被判为「不通过」。第一反应自然是：反向传播有 bug。

## 换成 float64，全过了

把实现切到 **float64** 重跑同一套梯度检查：

- forward / backward / 梯度裁剪 / Adam 单步：**688/688 分量全部通过**
- 显著梯度的最大相对误差约 **1e-6**

也就是说，反向传播是对的。float32 下那一堆「不通过」，是**精度问题，不是 bug**。

## 这套检查到底是怎么配的

「800+ 不通过 / 688 全过」不是随便来的数，它的口径写在 `test.js` 的 `gradCheck()` 里：

| 项目 | 值 |
|---|---|
| 模型配置 | `ctx=8 d=8 layers=1 heads=2 ffMul=2`（一个极小配置，便于逐分量核对） |
| 输入 | 固定 17 字短句，B=2、T=8，tokens/targets 手工铺排 |
| 有限差分步长 | `eps = 1e-5`，用 `(f(x+h) − f(x−h)) / (2h)` |
| 通过判据 | `相对误差 ≤ 1e-5 + 1e-4 × scale` |
| 检查范围 | 12 个参数张量（emb / pos / Wq0 / Wo0 / Wv0 / W1_0 / W2_0 / ln1g0 / ln2b0 / bq0 / lnfg / b2_0） |
| 分量总数 | 688 |

两点必须说清：

1. **步长 1e-5 正是 float32 吃不住的原因。** 差分要对相邻两个几乎相同的大数做减法，有效数字本来就被吃掉一截；再叠加 float32 的 24 位尾数，小梯度分量的噪声就盖过了信号。
2. **这里的「分量数」属于这个极小配置。** 换一个大模型，分量总数、被判定为「不通过」的数量、以及噪声占比都会变。所以 688 与 800+ 是**特定配置下的观测值**，不是通用数字。

## 为什么会「假失败」

有限差分本身是浮点减法：用 `(f(x+h) − f(x−h)) / (2h)` 这种相邻很近的两个大数相减，会损失大量有效数字。在 float32 下，这个量化噪声会**淹没掉那些量级很小的梯度分量**——它们相对误差被小分母放大，于是「看起来错了」。

而真正大的梯度分量，float32 下其实也对得上；出问题的恰恰是那些小而重要的分量。

## 项目里留下的开关

为了既能在浏览器里用 float32（省内存、够用），又能在调试时用 float64（梯度检查干净），`minilm.js` 加了一个 `MINILM_USE_F64` 开关：做数值对齐和梯度检查时开，正常训练和推理关。

## 给同样会手写反向传播的人的提醒

- 梯度检查的「FAIL」先别急着改公式，**先怀疑精度**：把实现切到 double 再跑一遍；
- float32 适合训练和推理，不适合当梯度检查的裁判；
- 奇怪的误差要先怀疑自己的代码，也先怀疑自己的**数值环境**——两者都查，才不会在错误的方向上改一天。

**可复现入口**：梯度检查 688/688 见 `minilm.js`（受 `MINILM_USE_F64` 控制）；PyTorch 侧 bitwise 对齐见 `py/verify_parity.py`（forward logits max|Δ|=5.55e-17）。
