# 续训后 loss 更低，不代表续训是对的

> **小白先读（2026-09-17 修订）**：恢复训练要比较状态和训练轨迹；某次 loss 更低可能只是换了轨迹，不能证明恢复正确。
> 本篇保留历史实验数字；“下一步”是当时的提议，不自动代表当前待办。先读[阅读地图](README.md)，现行能力看[项目状态](当前实现与历史结论.md)。

**系列：从零训练中文小说模型｜第 33 篇（实践篇·实验室周报）**
**前置阅读：原理篇 10（一次训练的账本：epoch、种子、过拟合与 checkpoint）、实践篇 28（checkpoint 不只是保存权重）、实践篇 32（种子没管住初始权重）**

实验身份：model=MiniLM-char-v1｜ctx=32｜batch=8｜lr=0.004｜seed=1234｜语料 story 桶前 24,000 字｜计划 160 步、中途点 80 步｜协议=「一次训完」vs「训一半再续训」逐位对比

上一轮发现 `py/train.py` 的随机种子设在了模型初始化之后。顺藤摸下去，同一个文件里的断点续训是更离谱的状态——它的实现是：

```
if args.resume:
    log(f'Resuming from step {start_step}; no retraining in this simple script.')
```

**这个「续训」什么都不训。** 而 checkpoint 里只存了 `model / itos / meta` 三样东西：没有优化器动量、没有 RNG 状态、没有学习率调度位置。就算把训练循环接上去，它也不是「接着上次跑」，而是「拿上次的权重重新开一次训练」。

## 先把验收标准定死

续训做得对不对，不该用「loss 看着还行」来判断。我用一个可以判死的标准：

> **一次训 160 步** 与 **训 80 步 → 存盘 → 从 checkpoint 续训到 160 步**，两者的末步权重必须**逐位相同**。

为了让它成立，还差一个前提：学习率调度必须**按计划总步数归一**。如果第一阶段按「总共 80 步」算 warmup 与余弦衰减、续训按「总共 160 步」算，那两段拼起来的 lr 曲线和一次训完根本不是同一条——所以加了 `--stop_at`：计划 160 步，第一阶段只停在第 80 步，调度形状保持一致。

## 结果

`py/verify_resume.py` 一次跑五条链，末步权重对基准 A（直接训 160 步）比：

| 变体 | 保存了什么 | step | 末步权重 max&#124;Δ&#124; | 探测 loss | Δloss vs A |
|---|---|---|---|---|---|
| **A 直训 160 步**（基准） | — | 160 | — | 5.2746 | — |
| **B 完整状态续训** | 权重+优化器+RNG+步数 | 160 | **0.000e+00** | 5.2746 | **+0.0000** |
| C1 丢 RNG | 权重+优化器 | 160 | 9.202e-02 | 5.2599 | **−0.0147** |
| C2 丢优化器 | 权重+RNG | 160 | 8.589e-02 | 5.3003 | +0.0257 |
| C3 旧格式（全丢） | 只有权重 | 160 | 1.154e-01 | 5.2903 | +0.0156 |

B 行是全篇的支点：**逐位一致，max|Δ| = 0.000e+00。** 续训做对了就是这样——不是「差不多」，是一个字节都不差。

C 组是失败样本，也是「修复前的真实处境」：修复前的 checkpoint 正好等于 C3（只有权重）。三条丢掉状态的链，参数漂移都在 0.09~0.12 量级——**它们不是「稍微差一点的续训」，是另外三次训练。**

## 最值得记住的一行

看 C1：**丢掉了 RNG 状态，续训后的探测 loss 比严格正确的续训还低 0.0147。**

这说明什么？说明模型确实在「另一条随机轨迹」上跑到了另一个点，而那个点碰巧好一点。如果我用「续训后 loss 更低」来证明续训正确，我会得出一个完全错的结论。

**loss 不是续训正确性的证据，逐位一致才是。** 这也是我把它做成自动判定脚本（`max|Δ|==0` 才算过）的原因——目测数字的宽容度太大了。

## 踩坑记录（顺序即真凶）

这条链我第一次跑出来是**失败**的（B 行 1.691e-01）。排查出三个独立原因，都值得记：

1. **验证脚本把中途 checkpoint 覆盖了。** 续训会把 `checkpoint.pt` 覆写成末步版本，C 组从被覆盖后的文件出发，等于「从终点续训」→ 三个变体全变成空操作，还都显示「参数一致」。**必须先把中途 checkpoint 备份再续训。**
2. **采样流与存盘流不是同一条。** 训练里 batch 起点用 `random.Random(seed)` 实例，而 `rng_state()` 存的是 python 全局模块的状态。两条流独立，恢复全局状态对采样毫无影响。改成统一用全局 RNG 之后才对上。
3. **续训没沿用语料规模。** 第一阶段 `--chars 24000`，续训那次没传 `--chars`，于是用了全量语料——**数据都不一样，还谈什么等价**。现在 `--chars` 会写进 meta，续训时不给就沿用 checkpoint 里的值，并打印差异告警。

这三条有一个共同点：**它们都不是「算法错了」，而是「账没记全」。** 续训的难点从来不是恢复权重，是把「这次训练的状态」完整地记在账上。

## 边界

- 本篇的逐位一致只在已测 CPU 环境成立。换设备、版本或非确定算法后，差异不保证始终极小；应先约定合理容差，同时核对数据、调度、优化器和轨迹，不能仅凭“换了设备”忽略较大漂移。
- 探测 loss 用的是固定窗口的 CE 平均，对参数差异敏感但不是评测指标；它只用来做 A/B 对照。
- 只在 24,000 字 / 160 步的最小设置上验证。长训练里优化器动量与 RNG 的耦合更深，等价性结论方向一致，但没实测到 10 万步级别。
- 没做的：断点续训的**跨设备**恢复（存 CUDA、续 CPU）。
