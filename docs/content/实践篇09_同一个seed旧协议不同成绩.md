# 同一个 seed，为什么旧评测协议会得出不同成绩？

> **小白先读（2026-09-17 修订）**：相同随机种子不能抵消评测规则的变化；比较成绩之前先比较试卷。
> 本篇保留历史实验数字；“下一步”是当时的提议，不自动代表当前待办。先读[阅读地图](README.md)，现行能力看[项目状态](当前实现与历史结论.md)。

**系列：从零训练中文小说模型｜第 9 篇（实践篇·实验室周报）**
**前置阅读：原理篇 11（评测与基线：留出集、Top-1、NLL 与 trigram）**

实验身份：model=MiniLM-char-v1｜corpus=记忆之海(2,668字)｜seed=42｜steps=400｜协议=旧(js_seed_run 打补丁)→新(eval/protocol.js)

「固定了 seed，结果就该可复现了吧？」——如果评测协议自己也变了，这句话就不成立。

## 一个让我警惕的数字

科幻语料，同一个 seed=42，同一个模型配置，留出集 Top-1 在新旧两套评测协议下分别是：

| 协议 | 科幻 Top-1 |
|---|---:|
| 旧协议 | 37.5% |
| 新协议 | 33.98% |

差 **3.5pt**。在这次实验记录里，这个协议迁移造成的偏移已经大于我们观察到的多数种子波动。**评测协议的改变足以制造出看似“模型变了”的差异。**

**一个容易困惑的地方**：本系列其它篇里出现的「科幻 34.0%」，就是这个 33.98% 的四舍五入。它们不是两次实验，是同一个数。

## 协议变了哪里

评测协议不是「算个准确率」那么简单，它至少包含：怎么切分训练/留出、每个位置能看到多少上文、窗口怎么滑动、损失和 Top-1 怎么累计。只要一边比另一边多看到一个字，分数就会悄悄变化——而且**不报错，只让结论悄悄错**。

这正是 PRD 点名的风险：模型和基线如果各写一遍评测，一边多看到一个字，对比就作废了。后来我们把协议收敛到唯一实现处（`eval/protocol.js` 的 `forEachWindow` / `forEachPosition` 同源），模型和 trigram 才真正站在同一条起跑线上。

## 代价：一批旧数据作废了

因为协议变了，原来那批 `js_*.json`（旧协议下跑的）不能和新数据混在一起比。我把它整批备份到 `dev/js_runs_oldprotocol/`，而不是悄悄丢掉——因为它仍然能回答「旧协议下模型长什么样」这个问题。

## 顺手得到的一个干净结论

做基线时发现一件好事：**加 α 平滑不影响 Top-1。** 同一个上下文下，分母是个常数，每个候选的分子统一 +α，argmax 的结果自然不变——受影响的只有 NLL。

这条很值钱，因为它意味着**挑 α 不可能把 Top-1 刷高**。基线和模型比 Top-1 这件事是干净的，不存在「我把基线的 α 调差了显得模型强」这条路。而 α 是在训练集尾部 10% 的开发集上挑的，没碰留出集。

所以从这次之后，我给自己定了一条很机械的习惯：**任何评测结果落盘时，同时记下协议实现的文件路径与函数名**（例如 `eval/protocol.js::forEachPosition`）。不写版本的协议，等于没有协议。

## 结论边界

- **固定的 seed 复现的是「同一条随机流」，不是「同一个结论」。结论还取决于协议、数据切分、可见上下文。**
- 任何「我换了实现/换了评测，结果变了」的对比，第一步要查的是：是不是协议也变了。
- 本观察基于 seed=42、科幻语料、字符级词表；其它语料在协议迁移下的偏移量级可能不同。

**可复现入口**：评测协议唯一实现见 `eval/protocol.js`；协议变更前后的结果分别在 `dev/js_runs_oldprotocol/` 和新版 `py/runs/` 里，可逐位置对账。
