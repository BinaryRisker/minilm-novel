# 容量对照：把主体放大 5 倍，Top-1 的缺口补上了吗？

> 日期：2026-09-14。实验文件：`py/sweep_worksplit.py`（`--tag big`）、对照脚本 `py/compare_cfg.py`。
> 语料：`data/splits/`（按作品整篇切分，无同作品泄漏）。
> 结果：`py/runs/wsplit_*_big_*.json`（75 条）、`py/runs/wsplit_summary_big.json`、
> `py/runs/wsplit_report_big.md`、`docs/img/worksplit_scaling_big.png`、`docs/img/worksplit_converge_big.png`。
> 前一轮（小主体，75 条）见 `docs/experiments/2026-09-14-worksplit-nll-converge.md`。

## 0. 一句话结论

**容量只解释了一小部分。** 在**训练数据 / 步数 / 种子 / 评测协议全部不变**、只把 Transformer 主体
从 **40,800 → 202,112** 参数（**4.95×**）之后：

- **≥5 万字档，5 个桶的 Top-1 一致变好**（对 trigram 的边距改善 **+0.3 ~ +3.4pt**）→ 说明**确实有一部分是容量问题**。
- **但缺口没有补上**：`gudian` 在每一档仍然输给 trigram（−0.4 ~ −3.5pt），
  而且 **1,000,000 字档的缺口反而变宽**（小主体 −4.5 → 大主体 −3.5，仍是大负）。
- **2,000 字档大主体一致更差**（Top-1 边距 −0.3 ~ −1.7pt，NLL 差 +0.6 ~ +1.4 nat）→ 数据太小时大主体是负担。
- **NLL 优势被放大**：`gudian` 1,000,000 字档 模型 − trigram 从 **−1.185 → −1.308 nat**，`wuxia` **−0.936 → −1.013**。
- 结论：**主因是结构（字符级 + 32 上下文 + "NLL 更准但峰值更尖"的指标错位），不是容量。**
  加容量能拿到 +0.5~+1.6pt，但拿不回 3.5pt 的缺口。

## 1. 协议：只动一个变量

| 变量 | 小主体（`tag=''`） | 大主体（`tag='big'`） |
|---|---|---|
| `cfg` | `d=40 layers=2 heads=4 ffMul=4` | `d=64 layers=4 heads=8 ffMul=4` |
| Transformer **主体**参数 | **40,800** | **202,112**（**4.95×**） |
| 含词表嵌入的总参数 | 111,560 ~ 295,960 | 315,328 ~ 610,368 |
| 训练数据 | 完全相同（同 `data/splits/` 前缀） | 同 |
| 步数 | 相同（`epochs × 字数 / (batch×ctx)`，下限 200） | 同 |
| 种子 | 1234 / 42 / 2024 | 同 |
| 评测 | 同一套留出切片与同一批评测位 | 同 |
| batch / lr | 32 / 0.004 | 同 |

**唯一变化的只有 `d / layers / heads`。** 这样得到的差值只能归因于容量。

> ⚠️ **这条"只动一个变量"是本轮最容易被破坏的地方**：我第一次启动时漏了
> `--cfg_d 64 --cfg_layers 4 --cfg_heads 8`，5 个进程空跑 **52 分钟**才发现产出的是小主体的重复件。
> 症状是对照表里两组数字逐格几乎逐位相同（Δ 恰好 0.000）。**现在 `compare_cfg.py` 会打印每组的
> cfg 与主体参数量**——这正是发现它的方式；启动后也应用 `head -1` 核对日志头里的 cfg。

## 2. 主结果：对 trigram 的边距（小主体 → 大主体）

`Top-1` 边距 = 模型 Top-1 − trigram(α=0.1) Top-1，**正数 = 模型赢**。
`Δ改善` = 大主体边距 − 小主体边距（正数 = 放大容量有帮助）。

| 桶 | 训练字数 | 小主体 | 大主体 | Δ改善 |
|---|---|---|---|---|
| `gudian` ✅ | 2,000 | −1.9 | −3.6 | **−1.7** |
| | 10,000 | −0.7 | −0.4 | +0.3 |
| | 50,000 | −2.0 | −1.5 | +0.5 |
| | 200,000 | −1.7 | **−0.1** | **+1.6** |
| | 1,000,000 | **−4.5** | **−3.5** | +1.0 |
| `wuxia` ✅ | 2,000 | −1.9 | −3.2 | −1.3 |
| | 10,000 | **+1.2** | −0.5 | −1.7 |
| | 50,000 | +0.1 | +0.6 | +0.5 |
| | 200,000 | +0.7 | **+1.3** | +0.6 |
| | 1,000,000 | +0.5 | **+1.1** | +0.6 |
| `urban` ✅ | 2,000 | −1.7 | −2.0 | −0.3 |
| | 10,000 | +0.7 | +0.6 | −0.1 |
| | 50,000 | −0.1 | +0.1 | +0.3 |
| | 200,000 | +0.1 | +0.7 | +0.7 |
| | 1,000,000 | −0.8 | −0.2 | +0.6 |
| `scifi` ⚠️C | 2,000 | +0.0 | −1.1 | −1.1 |
| | 10,000 | −1.4 | −0.8 | +0.7 |
| | 50,000 | −3.1 | −2.0 | +1.1 |
| | 200,000 | −0.5 | −0.2 | +0.2 |
| | 1,000,000 | −0.4 | **+0.4** | +0.9 |
| `story` ⚠️B | 2,000 | −1.9 | −2.8 | −0.9 |
| | 10,000 | −3.3 | −1.7 | +1.6 |
| | 50,000 | **−10.4** | −7.0 | **+3.4** |
| | 200,000 | −5.3 | −2.2 | +3.1 |

分级依据见 `docs/experiments/2026-09-14-worksplit-nll-converge.md` §9.3。）

`NLL` 边距 = 模型 NLL − trigram NLL，**负数 = 模型赢**：

| `wuxia` 小 → 大 | +0.806 → +1.406 | −0.733 → −0.536 | −0.881 → −0.880 | −1.060 → **−1.083** | −0.936 → **−1.013** |
| `urban` 小 → 大 | +0.096 → +1.472 | −0.748 → −0.620 | −0.845 → −0.805 | −0.890 → **−0.930** | −0.811 → **−0.877** |

## 3. 发现一：数据太少时，大主体是**负担**

2,000 字档上大主体在 **5/5 桶**都更差：Top-1 边距变差 0.3~1.7pt，NLL 变差 0.6~1.4 nat。
原因不是步数不够（同样是 200 步、约 100 个 epoch），而是**参数 / 字数比**：

- `gudian` 2,000 字 时，大主体总参数 61.0 万 ÷ 2,000 字 ≈ **305 参数/字**——纯记忆区间。
- 同一档小主体是 29.6 万 ÷ 2,000 ≈ 148 参数/字。**两者都在严重过拟合，参数越多越糟。**

含义：**"加容量"和"加数据"必须同时做**。在小数据档只看 Top-1 会得出"大模型更差"的错误结论。

## 4. 发现二：≥5 万字档，容量确实带来一致改善

从 50,000 字起，大主体在 **5/5 桶每一档**都改善了对 trigram 的 Top-1 边距（+0.3 ~ +3.4pt），
NLL 边距在 200,000 与 1,000,000 档也一致地更负。**所以"完全是结构问题"这个说法太强了**——
容量是有用的，只是**量级不够**。

排序上：改善最大的是 `story`（+3.0~+3.4，合成模板文本）与 `gudian` 200,000 档（+1.6）；
`wuxia`/`urban` 稳定拿到 +0.5~+0.7。

## 5. 发现三（决定性）：`gudian` 的缺口没被补上，而且在 100 万字档变**宽**了

这是本轮最关键的观察。看 `gudian` 的 Top-1 双线（模型两条 + trigram 一条）：

| 训练字数 | 模型 小主体 | 模型 大主体 | trigram |
|---|---|---|---|
| 200,000 | 11.9% | 13.5% | 13.6% |
| 1,000,000 | 16.7% | 17.7% | **21.2%** |

- 200,000 字时：大主体 **13.5% vs 13.6%** —— 几乎打平。
- 1,000,000 字时：**trigram 一口气从 13.6% 涨到 21.2%（+7.6pt）**，而模型从 13.5% 涨到 17.7%（+4.2pt）。
- 也就是说：**在这个桶上，越多数据，"背接字"的基线涨得越快**，缺口反而从 −0.1 扩大到 −3.5。

原因与前一轮 §9 的机制一致：`gudian` 是古典白话，固定搭配极多（"话说""看官""不在话下"）。
trigram 的 Top-1 本质是"`P(下一个字 | 最近两个字)` 的 argmax 命中率"，
**语料越大，它背下来的高频搭配越全，命中率单调上升**；模型用的是完整分布，Top-1 只是它的一个投影。

即：**加容量解决不了"指标口径"的差距。** 这也是为什么 NLL（模型更准）与 Top-1（模型更尖不过基线）会长期分歧。

补充：即便把 trigram 的 α 调到留出集上最优（α=0.01，属上界参考），`gudian` 1,000,000 字档
trigram 仍是 NLL 6.163 / Top-1 21.2% —— 模型 5.445 / 17.7%。**换成最强基线，NLL 赢 0.72 nat、Top-1 输 3.5pt 的格局不变。**

## 6. 发现四：容量放大的是 **NLL** 优势，不是 Top-1

对比两轮在最大档的表现（A 级桶，模型 − trigram）：

| 桶 | NLL 小 → 大 | Top-1 小 → 大 |
|---|---|---|
| `gudian` | −1.185 → **−1.308** | −4.5 → −3.5 |
| `wuxia` | −0.936 → **−1.013** | +0.5 → +1.1 |
| `urban` | −0.811 → **−0.877** | −0.8 → −0.2 |

**容量让 NLL 优势三条线全部继续扩大，而 Top-1 只补回一小截。**
这进一步支持"两把尺子量的不是同一件事"，而不是"模型不够大"。

## 7. 成本

| | 小主体 | 大主体 |
|---|---|---|
| 训练 CPU 合计（75 条） | 3.82 小时 | **8.44 小时（2.2×）** |
| 每条约 100 万字档 | 608s | **1310s** |
| 挂机（5 进程并行，4 核） | — | 1 小时 56 分 |

**注意：2.2× 的耗时换来的回报很小（A 级桶 100 万字档 +0.6~+1.0pt Top-1）。**
如果目标只是"跑通/对照"，小主体性价比高得多；要追上 Top-1，方向应转向结构（上下文、
目标函数、解码），而不是继续堆主体参数。

## 8. 结论

回到上一轮 `docs/experiments/2026-09-14-worksplit-nll-converge.md` §12 留的悬念
（"换更大的主体能不能追上 Top-1 未验证"）：

- **答案是"能改善，但追不上"。** 5× 主体在 ≥5 万字档一致带来 +0.3~+3.4pt 改善；
  但 A 级桶在最大档仍是 `gudian` −3.5 / `wuxia` +1.1 / `urban` −0.2，**缺口没有被填平**。
- **容量是次要变量。** 主因是：① 字符级 + 32 字上下文对长程依赖的表达有限；
  ② Top-1 这种"尖峰命中率"指标天然偏向 n-gram 的表面统计——**同一份模型在 NLL 上一直赢**。
- **优先级建议**：与其把主体再放大（2.2× 成本换 ~0.8pt），不如试
  ③ 加长上下文（`ctx` 32 → 64/128，直接针对"长程依赖"这条假设）、
  ④ 换指标/解码头（把 NLL 与 Top-1 都保留，但补一个 Top-1 之外的排序指标）、
  ⑤ 把数据量推到 500 万~800 万字（池子够：`gudian` 857 万、`wuxia` 551 万）。

## 9. 边界（不要外推）

- **没有调超参**。大主体仍用 `lr=0.004`、`batch=32`、无 warmup——这些是给小主体选的。
  大模型通常需要更小的 lr / 更长的 warmup。**所以"容量只值 +0.8pt"是"同超参下"的结论**，
  不排除调参后更好。这是本轮最大的保留项。
- **只放大到 20 万主体参数**（总参数 31.5 万~61.0 万）。"再放大 10 倍会怎样"没有答案。
- **`ctx` 固定 32**，所以"长程依赖不足"这条假设**没有被直接检验**，只是排除了"主体太小"这一条。
- **`scifi` / `story` 两桶的改善幅度不可当作能力证据**（前者跨域对照，后者合成模板文本）。
- **`gudian` 的"缺口变宽"依赖单条 trigram 曲线**（trigram 与种子无关，所以它没有误差棒；
  但它对 `α` 敏感，α 网格已在 §5 给出）。留出作品只有 5 部，作品级方差未被覆盖。

## 10. 复现命令

```bash
# 大主体（5 桶 × 5 档 × 3 种子；唯一变化是 cfg）
python py/sweep_worksplit.py --buckets all \
       --sizes 2000,10000,50000,200000,1000000 --seeds 1234,42,2024 --epochs 3 \
       --cfg_d 64 --cfg_layers 4 --cfg_heads 8 --tag big --no_report --no_plot
python py/sweep_worksplit.py --report_only --tag big   # → wsplit_report_big.md + worksplit_*_big.png

# 逐格对照（打印两组 cfg 与主体参数量，ΔTop-1 / ΔNLL）
python py/compare_cfg.py                    # 默认对比 tag='' 与 tag='big'
python py/compare_cfg.py --sizes 1000000    # 只看最大档
```

> `--tag` 会插进所有输出文件名（含图、报告、合并汇总），所以两套主体可以并列而不互相覆盖。
> 跨 `--tag` 复用 trigram 缓存是安全的（trigram 与 cfg 无关）：
> 把 `py/runs/wsplit_tri_<桶>_<档>_t<n>.json` 复制成 `..._big_t<n>.json` 即可跳过重算。
