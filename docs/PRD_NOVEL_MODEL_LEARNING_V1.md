# 小说模型、原理学习与公开实验：优化建议 V1

日期：2026-09-13。状态：审阅建议，尚未实施。本文用于补充和纠正旧路线，不代表实验已完成。

## 1. 文档目的与定位

把三个目标连起来：理解语言模型如何训练；逐步得到可控的小说生成能力；把真实实验积累成持续分享的内容。

建议对外定位为“从零训练一个中文故事模型，公开每次实验”。当前成果应表述为“约 5 万参数模型学到了局部字序、对话格式和题材词汇，仍有大量语病与逻辑漂移”。把“高质量长篇小说”作为远期目标。

审阅范围：README.md、原学习方案、中文小说生成测试报告.md、report_evidence.md、LOG.md，以及 minilm.js、test_novel.js、ui-src.html、dev/matmul.* 和已有基准输出。本轮没有重跑训练或重新验收全部功能。

## 2. 现状与最需要纠正的问题

| 优先级 | 现有问题与证据 | 建议 |
|---|---|---|
| P0 | 原方案称“限制从来不是参数量”“不需要更多算力” | 改成待验证假设。数据、容量、训练预算和任务难度共同限制能力；不要承诺小模型通过工程必然达到长篇质量目标。 |
| P0 | test_novel.js 仅将每篇末尾 10% 留出，并用均匀随机作对照 | 这是同篇尾段续写评估。增补训练集字频、平滑 bigram/trigram 对照；独立故事留出后才能研究跨故事泛化。记忆与局部泛化可以同时存在。 |
| P0 | minilm.js 的 encode 将未知字符变成 0，decode 跳过 0 | 模型输入保留了未知 token 的位置，但丢失字符身份。实际复现“警察敲了敲门，”编码为 [0,0,0,20,0,347,363]，解码为“了门，”。不能把这类输入当作完整语义的泛化测试。 |
| P0 | 词表由全文建立后才切分；只有约 200～270 个留出字符 | 披露词表使用了留出文本的字符集合；这不等于正文用于梯度训练，但“纯盲测”不准确。新增数据集先按故事分组切分，再只用训练部分训练 tokenizer。 |
| P0 | 初始化、批次和采样共用 Math.random；生成快照插在训练中 | 使用相互独立的随机流。否则增加一次演示采样也会改变后续训练批次，无法公平做实验。 |
| P0 | UI 把 loss 0.8～2.5 标成质量甜蜜点 | 只保留为历史观察，不能作为普适阈值或自动停止依据。用验证损失、重复率、复制比例和固定提示词样本共同判断。 |
| P1 | L0 只要求两边 Top-1 差 < 2pt | 用相同权重、输入、目标和数值精度核对 logits、loss、梯度和一次更新，再做训练趋势对照。两次独立随机训练的接近准确率不能证明实现正确。 |
| P1 | 原方案直接把结构编排收益套在 5.5 万参数模型上 | 目前模型没有指令训练，ctx=32 也容纳不了完整人物卡。先在能遵循指令的预训练模型上验证编排，再单独验证自研模型能否学会条件写作。 |
| P1 | README 把矩阵微基准推算出的“17 年／3 小时／4 元”并列展示 | JS 与 BLAS 的历史矩阵计时是真实记录；完整训练时间、租卡价格和小说能力是另一组问题。改成有条件估算，并用实际训练 tokens/s 与账单校准。 |

报告还把“不生成题材外词汇”解释为风格稳定，但封闭词表本身就限制了可生成的字。这一现象不能独立证明模型学会了风格控制。

原方案引用的《零号计划》全文与授权证据没有在本轮读取的项目文件中找到。先以仓库已有样例推进；外部作品和数据集标为候选，不视为已经准备好的训练输入。

## 3. 目标、非目标与成功定义

第一阶段目标：实验可复现、输入透明、评估可信、JS/PyTorch 数学对齐。

第二阶段目标：在范围受控的中文短故事上检验从零训练；同时建立预训练模型的小说续写对照。先做 300～800 字单场景：2～3 人物，一个冲突，一个结果。字数是项目阶段范围，不是能力保证。

暂不做：十亿参数从零预训练、立即生成 8000 字、GRPO 奖励系统、复杂多 Agent 平台、手机训练优化。DPO 在 SFT 已有效且拥有可靠偏好对后再考虑；GRPO 留作后续学习实验。

成功至少有三种独立证据：实现数值正确；未知故事上的预测与生成改善；读者盲评更偏好新版本。单独 loss 降低或生成更长都不能替代这些证据。

## 4. 双线架构与学习路径

### A 线：从零理解模型

保留 minilm.js 和浏览器实验台作为教学入口。新增 py/ 实现 PyTorch 对照，不要求长期维护两套全部现代架构。

顺序：可复现与评测 → 同权重平移 → tokenizer → 数据管线 → 小规模预训练 → 条件写作 SFT → 架构消融 → 可选偏好优化。

学习单元必须能回答一个问题：

- 分词：输入怎样变成 token，词表扩大会吃掉多少 embedding 参数？
- 前向与反向：logits 怎样变成 loss，梯度怎样改变下一字概率？
- 优化：同数据预算下，学习率、batch 与过拟合如何影响结果？
- 注意力：移除位置编码、缩短上下文，会破坏什么能力？热力图仅展示权重，不当作完整因果解释。
- 架构：一次只比较一个变化；SwiGLU 应匹配参数预算，GQA 应报告权重和 KV 两项变化，RoPE 不直接承诺长度外推质量。
- 后训练：预训练、SFT、偏好优化分别用了什么数据，训练目标如何变化？

规模先做可完整运行的小实验，再依据吞吐、显存和验证结果决定是否做 10M～50M。不要同时改分词器、架构、数据量再宣称某一个组件有效。

### B 线：小说能力对照

选一个已有中文能力、许可与硬件适配的预训练模型作为起点。本建议不锁定具体型号；正式实验时记录模型版本和模型卡。

四组逐级对照：原模型直接续写；原模型加人物卡与场景大纲；小说场景 SFT；SFT 加相同编排。至少保留“同一基座、同一输入信息、同一输出预算”的可比组。

每次输出注明：自研从零模型／预训练基座／微调版本／编排配置。外部模型生成的正文不能算作自研模型取得的能力。

先用固定脚本执行“场景计划 → 正文 → 人物状态更新”，无需先搭复杂 Agent 平台。人物名约束与字数约束应和情节合理性分开评价。

## 5. 数据、实验记录与评测

新增 data/manifest.jsonl 保存 story_id、source、provenance_note、content_hash、split、parent_story_id、teacher_model、prompt_version；字段用于追溯，未知信息明确留空并阻止纳入正式训练集。data/processed/ 保存清洗后的故事和大纲正文配对。

合成变体按 parent_story_id 分组，避免一个故事的改写落入测试集。大纲若由全文反向提取，记录来源，评测时只给预先可用设定，不把结局答案藏进输入。

runs/<run_id>/ 保存 config.json、metrics.jsonl、samples.jsonl、checkpoint、数据及 tokenizer 哈希、代码版本、设备、耗时、实际费用。随机种子至少覆盖初始化、批次、生成；每组主要结论先用 3 个种子探索，报告离散程度，不把它当作充分的统计证明。

评测分三层：

1. 数学：同权重前向、梯度、单步更新与存取一致性。
2. 语言：相同 tokenizer 下的验证 NLL、Top-1/5，字频与 n-gram 对照；不同 tokenizer 不直接比较 token PPL，可额外报告统一归一化的 bits/byte。
3. 故事：大纲事件完成率、人物事实矛盾、结尾完成度、重复片段比例、与训练文本的最长匹配片段，以及匿名 A/B 人工偏好。

先准备 30 个独立评测场景作探索集；之后新增锁定测试集。分别报告名字替换、事件组合变化、题材变化。人工盲评分开看通顺、因果、人物动机、可读性；随机左右顺序，允许平局，公开分母。LLM 裁判仅作辅助，并记录版本与提示词。

## 6. 用户流程、界面与移动端

访客打开实验台 → 看预录的同一提示词训练快照 → 查看原始输入与未知字符 → 调温度体验 → 查看对应实验卡与原始样本。

初学者模式只展示少量参数；进阶模式保留 loss、注意力、梯度检查。默认短演示，重训练由访客主动启动。分享卡至少含参数规模、数据量、种子、步数和“样例非质量保证”说明。

手机宽度 360/390px 下可操作生成与停止按钮，图表局部滚动，正文可复制。训练考虑 Worker，支持取消；恢复必须明确是重新开始还是从保存的 checkpoint 继续。

本阶段无需新增后端 API、数据库或任务中心。离线 CLI 保存 checkpoint 和日志即可。若以后引入 Web 训练服务，再设计任务 ID、进度事件/SSE、断线重连、取消和按任务 ID 重试；不在当前教学页面中预建平台。

## 7. 分享与反馈设计

建议主要面向“懂一点编程、想看懂大模型”的读者，内容主线是一个模型的成长史。每次实验同时产出：可复现代码、完整结果、一个可体验例子、一篇短复盘。

| 选题 | 必须拿出的证据 | 互动 |
|---|---|---|
| 我发现模型其实没看懂我输入的字 | 输入、token IDs、解码并排 | 读者试输入罕见字 |
| 5 万参数究竟学会了什么 | 随机、字频、n-gram、Transformer 对照 | 匿名猜输出来自哪一种 |
| 手写反向传播和 PyTorch 能对上吗 | 同权重 loss、梯度误差 | 可运行的最小例子 |
| loss 降了，故事为什么没变好 | 固定提示词、多种子、验证损失与复制率 | 读者盲选 checkpoint |
| 小模型能不能写完一场戏 | 固定人物与冲突，成功和失败样本 | 投稿新场景进入下一轮评测 |
| 我到底花了多少钱训练 | 实际账单、token 数、耗时 | 公布预算误差与失败尝试 |

默认每周围绕一个实验制作一篇长文和两段短演示；这是可调整的制作节奏，不是涨粉承诺。第一轮选择一个适合现有受众的平台，先验证反馈质量再扩散。

记录曝光 → 访问演示 → 开始体验 → 完成体验 → 返回或参与评测的转化。先收集两周基线，观察哪个选题带来复访与有效问题，不只追播放量。埋点和公网发布作为后续独立实施项，本轮不发布或收集访客数据。

## 8. 风险、成本与研究依据

优先使用已有原创样例和来源清楚的数据。旧文档中的数据许可、规模、现价及文风 GRPO 分数没有在本轮逐项核实，不沿用“已核实可用”的结论。

训练费用先测实际 step 时间、batch、ctx、有效 tokens/s、峰值内存，再按目标 token 数推算。总成本还包含预处理、数据生成、验证、重跑与空闲资源；本轮不租卡、不下载大模型。

研究支持的是方向，而非本项目性能保证：

- [TinyStories 原论文](https://arxiv.org/abs/2305.07759)：受限词汇的英文短故事可使很小的模型学习连贯生成；不能直接推出中文长篇质量，也不能推出规模无关。
- [StoryWriter 原论文](https://arxiv.org/abs/2506.16445)：大纲、规划和动态历史压缩用于长故事，摘要中数据平均长度为 8000 words，并使用 8B/9B 模型做 SFT；不是 5 万参数模型能写 8000 中文字的证据。
- [MiniMind 官方仓库](https://github.com/jingyaogong/minimind)：适合学习完整训练链路，其特定数据和配置的成本参考不能直接换算成这里的小说质量预算。

## 9. 阶段验收

第一关：固定种子可复现，演示采样不影响训练；未知字符可见；原始与修订报告分开保存。

第二关：同权重 PyTorch 与 JS 的数值对照通过，训练与验证链路可运行。

第三关：分组隔离数据与固定评测集就绪；独立故事评估给出模型与简单基线的完整比较。未超过简单基线也如实发布，不把结果包装成成功。

第四关：300～800 字单场景在人评与事实检查中获得可复验改善后，再扩到多场景、章节与长篇。阶段推进依据结果，不依赖预设日期。
